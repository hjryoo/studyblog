## 서론: 오늘 해결할 문제

두 요청이 같은 주문을 읽고 각각 수정하면 마지막 저장이 앞선 결정을 덮어쓸 수 있다.

영속성 컨텍스트의 동작을 알아야 저장과 조회의 실제 SQL을 예측할 수 있다. 프레임워크 기본값보다 업무 경계와 실행 결과를 우선한다.

## 1. 먼저 정할 모델과 계약

version 비교는 읽은 이후 상태가 바뀌었는지 검출한다. 충돌 검출과 어떤 변경을 다시 시도할지는 별도 정책이다.

## 2. 설계와 구현의 경계

변경 가능한 aggregate에 version을 두고 충돌은 업무 응답으로 번역한다. 재시도 시 최신 상태로 규칙을 다시 검증한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
@Entity
class Order {
  @Id Long id;
  @Version Long version;
  String status;
}
// 변경 SQL에 이전 version 조건이 사용됨
```

같은 version에서 시작한 두 transaction 중 하나가 충돌하는지 확인한다.

## 4. 자주 실패하는 방식

낙관적 잠금 예외를 무조건 재시도하면 이미 실행한 외부 부작용이 중복될 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

version 충돌률, 재시도 횟수와 동일 업무 키 중복 처리를 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

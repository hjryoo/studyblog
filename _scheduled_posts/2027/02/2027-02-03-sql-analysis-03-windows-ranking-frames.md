## 서론: 오늘 해결할 문제

동률 데이터가 추가된 뒤 누적 합계가 한 번에 뛰거나 순위 개수가 예상과 달라진다.

주문·정산 리포트의 정확성은 행의 의미와 집계 기준에 달려 있다. 작은 반례 데이터로 결과를 먼저 검증한 뒤 실행 비용을 비교한다.

## 1. 먼저 정할 모델과 계약

PARTITION은 계산 집합을 나누고 ORDER BY와 frame은 그 안의 계산 범위를 정한다. 순위 함수마다 동률 처리도 다르다.

## 2. 설계와 구현의 경계

누적 합계에는 ROWS 범위와 안정적인 동률 정렬 키를 명시한다. ROW_NUMBER와 RANK의 업무 의미를 구분한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```sql
SELECT id, SUM(amount) OVER (
  PARTITION BY account_id
  ORDER BY occurred_at, id
  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
) AS running_total
FROM ledger;
```

동일 시각 거래 여러 건을 넣어 기본 frame과 명시한 ROWS 결과를 비교한다.

## 4. 자주 실패하는 방식

정렬 키가 유일하지 않으면 같은 입력에도 행별 누적 결과가 불안정할 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

전체 합계와 마지막 누적값, 동률 순위와 실행 계획의 정렬 비용을 검증한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

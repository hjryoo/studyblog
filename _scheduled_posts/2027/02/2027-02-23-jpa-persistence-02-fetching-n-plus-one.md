## 서론: 오늘 해결할 문제

목록 한 번을 읽었는데 각 항목의 연관 정보를 접근할 때 SQL이 반복된다.

영속성 컨텍스트의 동작을 알아야 저장과 조회의 실제 SQL을 예측할 수 있다. 프레임워크 기본값보다 업무 경계와 실행 결과를 우선한다.

## 1. 먼저 정할 모델과 계약

객체 탐색 경로와 실제 조회 범위는 다르다. 기본 fetch 설정만으로 모든 화면을 효율적으로 제공할 수 없다.

## 2. 설계와 구현의 경계

화면별 DTO projection 또는 fetch plan을 정의한다. 컬렉션 fetch join과 페이지 처리의 제한도 확인한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
public interface OrderSummary {
  Long getId();
  String getCustomerName();
}
// 화면에 필요한 필드만 조회하는 전용 query와 연결
```

목록 크기를 1·10·100으로 늘려 SQL 횟수가 어떻게 변하는지 비교한다.

## 4. 자주 실패하는 방식

모든 관계를 EAGER로 바꾸면 필요 없는 그래프까지 읽고 다른 경로에 N+1을 옮길 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

요청당 SQL 수, 반환 행 수, 응답 크기와 query 시간을 측정한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

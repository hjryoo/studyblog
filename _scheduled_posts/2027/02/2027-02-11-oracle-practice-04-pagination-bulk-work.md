## 서론: 오늘 해결할 문제

변경되는 테이블을 OFFSET으로 순회하면 중간 삽입·삭제로 누락이나 중복이 생긴다.

Oracle 기반 업무 시스템의 조회와 변경을 작은 트랜잭션으로 검증한다. DB 제품별 동작 차이를 추측하지 않고 대상 환경에서 확인한다.

## 1. 먼저 정할 모델과 계약

안정된 키 순서와 처리 범위가 있어야 대량 작업의 진행을 설명할 수 있다. 재시작 위치는 메모리 밖에 남긴다.

## 2. 설계와 구현의 경계

증가 키와 필요하면 상한선을 고정해 keyset 방식으로 처리한다. commit 단위를 작게 나누고 멱등성을 보장한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```sql
SELECT id, status
FROM orders
WHERE id > :last_id AND id <= :upper_id
ORDER BY id
FETCH FIRST 500 ROWS ONLY;
-- 처리 성공한 마지막 id를 checkpoint에 기록
```

작업 도중 새 행을 넣고 삭제한 뒤 재시작해 원래 대상 집합의 처리 결과를 대사한다.

## 4. 자주 실패하는 방식

수백만 행을 한 트랜잭션으로 갱신하면 undo와 잠금, 복구 부담이 커진다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

chunk 시간, checkpoint, 처리량, 누락·중복과 undo 사용을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

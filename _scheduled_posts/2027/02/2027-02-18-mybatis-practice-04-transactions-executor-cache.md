## 서론: 오늘 해결할 문제

동일 조회 결과가 바뀌지 않는 현상을 DB 문제로 보지만 실제로는 세션 캐시일 수 있다.

명시적 SQL의 장점을 유지하면서 매핑·입력·트랜잭션 계약을 검사한다. 동적 조합이 늘수록 대표 SQL과 경계 입력을 테스트에 남긴다.

## 1. 먼저 정할 모델과 계약

SqlSession과 트랜잭션 수명, local cache 범위를 함께 이해해야 읽기와 쓰기의 가시성을 설명할 수 있다.

## 2. 설계와 구현의 경계

Spring 연동에서는 관리되는 mapper와 transaction 경계를 사용한다. 직접 연 세션과 수동 commit을 섞지 않는다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
요청 시작
  → Spring transaction
  → mapper 조회·변경
  → DB commit 또는 rollback
  → 세션 정리
실제 SQL 실행 로그와 객체 반환을 따로 확인
```

같은 세션의 반복 조회와 다른 트랜잭션의 갱신을 교차해 캐시·DB 관측 차이를 확인한다.

## 4. 자주 실패하는 방식

SqlSession을 여러 스레드에서 직접 공유하거나 세션 밖 객체 변경을 추적할 것이라 기대하지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

SQL 실행 횟수, 세션 범위, cache 설정과 트랜잭션 종료를 함께 기록한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

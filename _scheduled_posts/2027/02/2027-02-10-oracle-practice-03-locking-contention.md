## 서론: 오늘 해결할 문제

재고 한 행을 수정하는 트랜잭션이 외부 API를 기다리면 다른 주문까지 멈춘다.

Oracle 기반 업무 시스템의 조회와 변경을 작은 트랜잭션으로 검증한다. DB 제품별 동작 차이를 추측하지 않고 대상 환경에서 확인한다.

## 1. 먼저 정할 모델과 계약

행 잠금은 변경 경쟁을 조율하지만 잠금을 보유하는 시간이 곧 다른 요청의 대기 시간이 된다.

## 2. 설계와 구현의 경계

일관된 잠금 획득 순서와 짧은 트랜잭션을 사용한다. NOWAIT와 WAIT 선택은 실패를 처리할 정책과 함께 정한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```sql
SELECT available
FROM inventory
WHERE sku = :sku
FOR UPDATE NOWAIT;
-- 획득 실패는 제한된 재시도 또는 업무 오류로 처리
```

두 세션이 같은 재고를 잡는 상황을 재현하고 거절·재시도 시간을 확인한다.

## 4. 자주 실패하는 방식

잠금 대기를 무한히 허용하거나 트랜잭션 안에서 느린 외부 호출을 수행하면 장애가 전파된다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

blocking 세션, 대기 이벤트, 잠금 지속 시간과 재시도 증폭을 추적한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 서론: 오늘 해결할 문제

동일 요청 안의 두 SELECT가 항상 같은 데이터 집합을 본다고 가정하면 대사 결과가 흔들린다.

Oracle 기반 업무 시스템의 조회와 변경을 작은 트랜잭션으로 검증한다. DB 제품별 동작 차이를 추측하지 않고 대상 환경에서 확인한다.

## 1. 먼저 정할 모델과 계약

기본 READ COMMITTED에서 문장 단위 읽기 일관성과 트랜잭션 전체 snapshot은 다르다. undo는 과거 값을 구성하는 데 쓰인다.

## 2. 설계와 구현의 경계

한 번의 조회로 필요한 결과를 만들거나 업무에 맞는 일관성 범위를 선택한다. 긴 리포트의 보존 요구도 확인한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
세션 A: 첫 SELECT 실행
세션 B: 행 변경 후 COMMIT
세션 A: 두 번째 SELECT 실행
READ COMMITTED에서 두 문장의 결과가 달라질 수 있음
업무상 필요한 snapshot 범위를 별도로 정의
```

두 세션에서 갱신과 반복 조회를 교차 실행해 각 문장의 관측 결과를 기록한다.

## 4. 자주 실패하는 방식

긴 SELECT가 항상 영원히 과거 데이터를 읽을 수 있다고 가정하면 snapshot too old를 놓친다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

조회 지속 시간, undo 압박과 일관성 관련 오류를 같은 시간축으로 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

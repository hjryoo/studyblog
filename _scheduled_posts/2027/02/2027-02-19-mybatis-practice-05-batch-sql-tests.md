## 서론: 오늘 해결할 문제

Java 메서드가 성공했어도 batch 실행 오류는 flush나 commit에서 뒤늦게 발생할 수 있다.

명시적 SQL의 장점을 유지하면서 매핑·입력·트랜잭션 계약을 검사한다. 동적 조합이 늘수록 대표 SQL과 경계 입력을 테스트에 남긴다.

## 1. 먼저 정할 모델과 계약

batch는 여러 요청을 모아 처리하는 방식이며 오류 위치와 성공 범위를 별도로 해석해야 한다.

## 2. 설계와 구현의 경계

동일 SQL 구조를 묶고 주기적으로 flush한다. 실패 시 전체 transaction 정책과 재시작 가능한 업무 키를 정한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
입력 검증
  → 동일 SQL batch 구성
  → 명시적 flush
  → 결과·예외 확인
  → transaction commit
실패 시 업무 키로 멱등 재처리
```

중간 행에 제약 위반을 넣어 실제 rollback 범위와 재실행 결과를 확인한다.

## 4. 자주 실패하는 방식

update 반환값을 모든 행의 최종 성공 증거로 사용하면 지연 실행 의미를 놓친다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

flush 시간, batch 크기, 제약 오류와 재처리 중복을 검증한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

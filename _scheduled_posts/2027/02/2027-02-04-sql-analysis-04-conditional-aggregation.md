## 서론: 오늘 해결할 문제

전체 주문 수와 상태별 주문 수를 서로 다른 쿼리로 읽으면 기준 시각과 조건이 갈라진다.

주문·정산 리포트의 정확성은 행의 의미와 집계 기준에 달려 있다. 작은 반례 데이터로 결과를 먼저 검증한 뒤 실행 비용을 비교한다.

## 1. 먼저 정할 모델과 계약

분모·분자와 한 행의 집계 단위를 동일하게 정의해야 비율이 의미를 갖는다. 취소와 미완료의 포함 여부를 명시한다.

## 2. 설계와 구현의 경계

기준 데이터 집합을 CTE로 고정하고 CASE 또는 지원되는 FILTER로 여러 지표를 계산한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```sql
SELECT COUNT(*) AS total,
  SUM(CASE WHEN status = 'PAID' THEN 1 ELSE 0 END) AS paid,
  SUM(CASE WHEN status = 'CANCELLED' THEN 1 ELSE 0 END) AS cancelled
FROM orders
WHERE created_at >= :from AND created_at < :until;
```

전체가 0인 경우와 결제 완료만 있는 경우를 검사한다. 정수 나눗셈으로 비율이 잘리지 않게 한다.

## 4. 자주 실패하는 방식

다른 기간과 timezone으로 분자·분모를 조회하면 성공률이 왜곡된다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

상태별 합과 전체 건수, 분모 0 처리, 리포트 기준일을 확인한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현

  → 관측 결과 비교
  → 운영 절차에 반영
```

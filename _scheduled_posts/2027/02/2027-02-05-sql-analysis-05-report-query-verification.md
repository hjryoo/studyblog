## 서론: 오늘 해결할 문제

작은 테스트에서는 맞던 리포트가 데이터가 쌓인 뒤 시간 초과와 메모리 사용 급증을 만든다.

주문·정산 리포트의 정확성은 행의 의미와 집계 기준에 달려 있다. 작은 반례 데이터로 결과를 먼저 검증한 뒤 실행 비용을 비교한다.

## 1. 먼저 정할 모델과 계약

결과의 정확성과 실행 자원 사용은 별도의 검증 대상이다. 분석 함수와 정렬도 읽는 데이터량에 따라 비용이 커진다.

## 2. 설계와 구현의 경계

대표 분포와 최악의 편중 데이터를 준비하고 기간·열·행 수를 제한한다. 실제 실행 검사는 통제된 환경에서 수행한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT account_id, SUM(amount)
FROM ledger
WHERE occurred_at >= :from AND occurred_at < :until
GROUP BY account_id;
-- ANALYZE는 실제 실행하므로 검증 환경에서 수행
```

같은 리포트의 결과 해시와 총계를 고정하고 데이터량을 늘려 실행 계획 변화를 비교한다.

## 4. 자주 실패하는 방식

실행 계획의 추정 비용을 밀리초로 해석하거나 운영에서 무제한 분석 쿼리를 실행하지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

실제 행 수, 추정 오차, 정렬 spill, 읽기량과 취소 시간을 기록한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

## 서론: 오늘 해결할 문제

값만 다른 SQL 문자열이 계속 생성되면 파싱 비용과 공유 영역 사용이 커진다.

Oracle 기반 업무 시스템의 조회와 변경을 작은 트랜잭션으로 검증한다. DB 제품별 동작 차이를 추측하지 않고 대상 환경에서 확인한다.

## 1. 먼저 정할 모델과 계약

bind 변수는 값과 SQL 구조를 분리한다. 다만 데이터 편중이 심하면 모든 값에 같은 실행 전략이 유리하지 않다.

## 2. 설계와 구현의 경계

일반 입력은 bind로 전달하고 대표 선택도별 실행 계획과 통계를 확인한다. 문자열 연결로 조건 값을 만들지 않는다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```sql
SELECT id, status
FROM orders
WHERE tenant_id = :tenant_id
  AND status = :status
ORDER BY id;
-- 값은 드라이버 bind API로 전달
```

희소 값과 흔한 값으로 같은 SQL을 실행하고 실제 읽기량을 비교한다.

## 4. 자주 실패하는 방식

bind를 사용했다는 사실만으로 최적의 계획과 SQL injection 방어 전체가 보장되는 것은 아니다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

parse 횟수, SQL 변형 수, 실제 행 수와 계획별 지연을 추적한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현

```

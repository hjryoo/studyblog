## 서론: 오늘 해결할 문제

애플리케이션 롤백으로 DDL까지 취소될 것이라 생각하면 운영 schema가 예상과 달라진다.

Oracle 기반 업무 시스템의 조회와 변경을 작은 트랜잭션으로 검증한다. DB 제품별 동작 차이를 추측하지 않고 대상 환경에서 확인한다.

## 1. 먼저 정할 모델과 계약

Oracle의 DDL은 일반 DML과 동일한 롤백 단위로 다룰 수 없다. 암묵적 commit과 객체 잠금의 영향을 확인한다.

## 2. 설계와 구현의 경계

schema 변경을 애플리케이션 배포와 분리하고 역호환 기간을 둔다. 새 컬럼 추가·backfill·사용 전환·정리를 단계화한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
배포 1: 새 컬럼 추가
별도 작업: 제한된 backfill
배포 2: 새 컬럼 읽기 시작
검증: 이전 버전과 동시 동작
정리: 사용 중단 확인 후 제거
```

대표 데이터로 DDL 잠금 시간과 이전 버전 실행을 시험한다. 실패 시 복구 SQL을 별도로 검토한다.

## 4. 자주 실패하는 방식

운영에서 즉석 DDL과 데이터 정정을 한 세션에 섞으면 의도하지 않은 commit이 생길 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

DDL 대기 시간, invalid 객체, 이전 버전 호환성과 backfill 불일치를 확인한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

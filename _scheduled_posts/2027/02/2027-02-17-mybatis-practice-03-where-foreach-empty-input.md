## 서론: 오늘 해결할 문제

검색 조건이 모두 비거나 IN 목록이 비었을 때 SQL 의미가 전체 조회로 바뀔 수 있다.

명시적 SQL의 장점을 유지하면서 매핑·입력·트랜잭션 계약을 검사한다. 동적 조합이 늘수록 대표 SQL과 경계 입력을 테스트에 남긴다.

## 1. 먼저 정할 모델과 계약

동적 문법의 유효성과 업무상 허용 범위는 다른 조건이다. 빈 목록은 전체·빈 결과·오류 중 하나로 명시해야 한다.

## 2. 설계와 구현의 경계

서비스 경계에서 필수 조건과 최대 목록 길이를 검증한다. XML의 where와 foreach는 구문 생성을 맡긴다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```xml
<where>
  tenant_id = #{tenantId}
  <if test="ids != null and ids.size() > 0">
    AND id IN
    <foreach item="id" collection="ids" open="(" separator="," close=")">
      #{id}
    </foreach>
  </if>
</where>
```

null·빈 목록·한 건·상한 초과 입력을 각각 실행한다. 빈 목록이 무조건 필터 생략이 되지 않게 한다.

## 4. 자주 실패하는 방식

IN 조건만 선택적으로 제거하면 의도하지 않은 전체 조회나 대량 갱신이 가능해진다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

조건 없는 SQL 실행, 조회 상한 초과와 목록 크기 분포를 추적한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

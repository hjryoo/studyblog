## 서론: 오늘 해결할 문제

제외 목록에 NULL 하나가 섞였을 뿐인데 NOT IN 조회가 기대와 다르게 빈 결과를 낸다.

주문·정산 리포트의 정확성은 행의 의미와 집계 기준에 달려 있다. 작은 반례 데이터로 결과를 먼저 검증한 뒤 실행 비용을 비교한다.

## 1. 먼저 정할 모델과 계약

SQL 조건에는 true·false뿐 아니라 unknown이 있다. WHERE는 true인 행만 통과시킨다.

## 2. 설계와 구현의 경계

NULL 허용 여부를 schema와 입력 계약에 적고 제외 조건은 의도에 맞는 NOT EXISTS로 표현한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```sql
SELECT o.id
FROM orders o
WHERE NOT EXISTS (
  SELECT 1 FROM blocked_orders b
  WHERE b.order_id = o.id
);
```

제외 목록에 NULL, 동일 ID, 다른 ID를 각각 넣어 결과를 비교한다.

## 4. 자주 실패하는 방식

COALESCE로 임의의 기본값을 채우면 실제 기본값 데이터와 미지정 상태가 섞인다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

NULL 비율과 제외 전후 건수를 확인한다. COUNT(*)와 COUNT(column)의 차이도 검사한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 서론: 오늘 해결할 문제

주문에 결제와 항목을 동시에 조인하면 두 일대다 관계가 곱해져 합계가 커진다.

주문·정산 리포트의 정확성은 행의 의미와 집계 기준에 달려 있다. 작은 반례 데이터로 결과를 먼저 검증한 뒤 실행 비용을 비교한다.

## 1. 먼저 정할 모델과 계약

조인 결과 한 행이 무엇을 뜻하는지 먼저 정한다. 서로 다른 집계 단위를 섞으면 DISTINCT만으로 정확성을 복구하기 어렵다.

## 2. 설계와 구현의 경계

각 자식 테이블을 주문 단위로 먼저 집계한 뒤 결합한다. 존재 확인만 필요하면 EXISTS로 의도를 표현한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```sql
WITH paid AS (
  SELECT order_id, SUM(amount) total
  FROM payments GROUP BY order_id
)
SELECT o.id, p.total
FROM orders o LEFT JOIN paid p ON p.order_id = o.id;
```

항목 두 개와 결제 세 건인 주문을 넣고 조인 행 여섯 개가 되는 반례를 확인한다.

## 4. 자주 실패하는 방식

SUM(DISTINCT amount)는 우연히 같은 금액인 서로 다른 결제를 하나로 합친다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

입력 관계의 키 유일성과 조인 전후 행 수, 금액 합계를 비교한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

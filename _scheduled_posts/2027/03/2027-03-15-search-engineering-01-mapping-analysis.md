## 서론: 오늘 해결할 문제

필드가 동적으로 생성된 뒤 타입을 잘못 정한 사실을 알면 전체 재색인이 필요할 수 있다.

검색 결과는 DB 원본, 색인 지연, 분석기와 질의가 결합된 산출물이다. 사용자의 검색 의도와 운영 비용을 함께 검증한다.

## 1. 먼저 정할 모델과 계약

text는 분석된 검색용이고 keyword는 정확 일치·정렬·집계에 쓰는 표현이다.

## 2. 설계와 구현의 경계

검색·필터·정렬 요구를 먼저 적고 중요한 필드는 명시적 mapping을 사용한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```json
{"mappings":{"properties":{
  "title":{"type":"text"},
  "sku":{"type":"keyword"},
  "tenant_id":{"type":"keyword"}
}}}
```

공백·대소문자·한국어 입력과 정확한 상품 코드를 각각 검색한다.

## 4. 자주 실패하는 방식

사용자 임의 필드를 전부 mapping으로 확장하면 필드 수와 관리 비용이 폭증한다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

필드 수, 분석 토큰, 색인 거절과 query별 결과를 검사한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

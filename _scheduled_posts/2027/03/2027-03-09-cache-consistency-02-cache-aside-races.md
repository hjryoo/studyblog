## 서론: 오늘 해결할 문제

갱신 후 캐시를 삭제해도 느린 이전 조회가 뒤늦게 옛값을 다시 넣을 수 있다.

캐시는 데이터의 복사본이며 원본과 다른 수명과 실패 방식을 갖는다. 적중률뿐 아니라 얼마나 오래 잘못된 값을 허용하는지 설계한다.

## 1. 먼저 정할 모델과 계약

원본 쓰기와 캐시 무효화는 서로 다른 연산이다. 실행 순서만 정했다고 원자성이 생기지 않는다.

## 2. 설계와 구현의 경계

TTL로 영향 시간을 제한하고 정합성이 중요한 경우 버전 확인이나 원본 검증을 추가한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
A: DB에서 version 10 읽고 대기
B: DB version 11 commit
B: cache 삭제
A: version 10을 cache에 저장
대응: 신선도 예산 + 검증 가능한 버전 정책
```

읽기 A를 지연시키고 쓰기 B와 삭제를 먼저 끝내는 교차 순서를 재현한다.

## 4. 자주 실패하는 방식

삭제를 두 번 하면 모든 경쟁이 해결된다고 보장할 수 없다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

갱신 직후 stale read, 버전 역행과 cache refill 지연을 측정한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

## 서론: 오늘 해결할 문제

업로드 URL을 발급했어도 서버가 파일을 받았고 검증했다는 뜻은 아니다.

파일 바이트와 업무 상태를 분리하고 업로드·검증·공개·삭제의 수명주기를 관리한다. 객체 저장소를 사용해도 권한과 정합성 책임은 남는다.

## 1. 먼저 정할 모델과 계약

서명 URL은 발급자의 권한을 한정해 전달하는 bearer 권한이다. 같은 키 재사용과 만료를 고려한다.

## 2. 설계와 구현의 경계

고유 객체 키와 짧은 유효기간을 사용한다. 크기·checksum 제한은 선택한 API가 실제 강제하는 항목으로 검증한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
인증·인가
  → 서버가 고유 uploadId와 objectKey 생성
  → 제한된 PUT 권한 발급
  → client가 직접 업로드
  → 서버가 객체 정보 확인 후 완료 승인
```

만료·다른 키·다른 메서드 요청과 같은 URL 재사용을 시험한다.

## 4. 자주 실패하는 방식

URL을 한 번만 쓸 수 있다고 가정하면 덮어쓰기와 재업로드를 놓친다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

발급 대비 업로드 성공, 만료 실패, 크기 위반과 URL 로그 노출을 검사한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.

- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

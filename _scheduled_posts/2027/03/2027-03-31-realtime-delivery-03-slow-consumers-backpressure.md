## 서론: 오늘 해결할 문제

느린 클라이언트에게 모든 이벤트를 쌓아 두면 서버 메모리가 고갈된다.

알림과 진행 상태 전송은 연결 유지보다 재접속·권한·과부하 처리가 어렵다. 연결과 업무 이벤트의 수명을 분리한다.

## 1. 먼저 정할 모델과 계약

메시지 종류별로 유실·병합·재생 가능성을 정해야 backpressure 정책을 선택할 수 있다.

## 2. 설계와 구현의 경계

연결당 큐와 전송 timeout을 제한한다. 진행률처럼 최신 값이 중요한 정보는 중간 값을 병합한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
진행률: 10 → 20 → 30 → 최신 30으로 병합 가능
업무 완료: 영구 상태 저장 후 이벤트 발행
큐 한도 초과: 연결 종료 + 재접속 안내
재접속: 마지막 확인 위치부터 복구
```

한 client의 수신을 늦추고 다른 연결 지연과 메모리가 영향을 받는지 확인한다.

## 4. 자주 실패하는 방식

결제 완료와 단순 진행률을 같은 drop 정책으로 처리하면 중요한 사건이 사라진다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

연결별 큐 길이, 병합·drop 수, 메모리와 느린 연결 종료를 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

## 서론: 오늘 해결할 문제

사용자 파일명을 객체 키로 그대로 사용하면 충돌과 경로 추측, 덮어쓰기가 생긴다.

파일 바이트와 업무 상태를 분리하고 업로드·검증·공개·삭제의 수명주기를 관리한다. 객체 저장소를 사용해도 권한과 정합성 책임은 남는다.

## 1. 먼저 정할 모델과 계약

업무 파일 ID, 사용자 표시 이름, 저장소 객체 키는 서로 다른 식별자다.

## 2. 설계와 구현의 경계

서버가 고유 키와 소유 tenant를 정하고 DB에 연결한다. 사용자 이름은 메타데이터로 제한해 저장한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
fileId: f-42
tenant: t1
displayName: report.pdf
objectKey: tenants/t1/uploads/f-42/source
state: PENDING
표시 이름과 저장 키를 직접 결합하지 않음
```

동일 이름 업로드와 다른 tenant 접근을 시험하고 파일 ID로 인가되는지 확인한다.

## 4. 자주 실패하는 방식

UUID처럼 추측하기 어려운 ID도 접근 권한 검사를 대체하지 못한다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

키 충돌, 소유권 불일치와 파일 상태별 객체 존재를 대조한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

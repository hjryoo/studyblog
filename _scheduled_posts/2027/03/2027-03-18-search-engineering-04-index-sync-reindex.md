## 서론: 오늘 해결할 문제

색인 전체 재구축 중 들어온 변경을 놓치면 새 인덱스가 오래된 값으로 전환된다.

검색 결과는 DB 원본, 색인 지연, 분석기와 질의가 결합된 산출물이다. 사용자의 검색 의도와 운영 비용을 함께 검증한다.

## 1. 먼저 정할 모델과 계약

검색 인덱스는 재구축 가능한 읽기 모델이다. 원본 버전과 증분 변경의 적용 위치가 필요하다.

## 2. 설계와 구현의 경계

snapshot 범위와 변경 stream의 연결 지점을 기록하고 중복·역순 변경을 버전으로 다룬다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
원본 snapshot + 변경 위치 저장
  → 새 인덱스 bulk 적재
  → 증분 변경 catch-up
  → 삭제·표본 데이터 검증
  → alias 전환, 이전 인덱스 보존
```

재색인 도중 수정·삭제를 넣고 원본과 문서 수·표본 필드를 대사한다.

## 4. 자주 실패하는 방식

문서 수가 같아도 내용과 삭제 상태가 다를 수 있으므로 건수만으로 완료하지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

색인 lag, 버전 역행 거절, 삭제 누락과 대사 불일치를 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

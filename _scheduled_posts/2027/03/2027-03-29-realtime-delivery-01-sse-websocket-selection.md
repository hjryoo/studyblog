## 서론: 오늘 해결할 문제

단방향 진행 알림에도 양방향 세션 프로토콜을 도입하면 운영 책임만 늘 수 있다.

알림과 진행 상태 전송은 연결 유지보다 재접속·권한·과부하 처리가 어렵다. 연결과 업무 이벤트의 수명을 분리한다.

## 1. 먼저 정할 모델과 계약

SSE는 HTTP 기반 서버 발신 스트림이고 WebSocket은 양방향 메시지 연결이다.

## 2. 설계와 구현의 경계

단방향 진행 정보와 양방향 상호작용을 나누고 proxy·client 지원, 재접속 요구를 검토한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
id: 42
event: progress
data: {"jobId":"j1","percent":50}

SSE 이벤트는 빈 줄로 구분
이벤트 ID와 업무 상태는 서버에 별도 보관
```

작업 진행 알림을 SSE로 만들고 연결 종료 후 다시 접속하는 흐름을 확인한다.

## 4. 자주 실패하는 방식

연결이 살아 있다는 이유로 업무 이벤트가 영구 저장됐다고 보장하지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

연결 수, 재접속, 이벤트 지연과 전달 누락을 분리해 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

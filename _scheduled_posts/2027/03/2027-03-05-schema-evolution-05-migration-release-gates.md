## 서론: 오늘 해결할 문제

migration 도구의 성공 표시만으로 데이터 의미와 이전 버전 호환성까지 검증되지는 않는다.

실행 중인 이전·새 애플리케이션이 같은 DB를 쓰는 상황을 전제로 변경한다. schema와 데이터 이관의 완료 조건을 분리한다.

## 1. 먼저 정할 모델과 계약

schema 이력, 데이터 대사와 애플리케이션 호환은 별도의 증거다.

## 2. 설계와 구현의 경계

변경 파일은 배포 후 수정하지 않고 새 이력으로 정정한다. 전환 전 불변 조건과 rollback 가능 지점을 고정한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
Gate 1: schema 이력 검증
Gate 2: backfill 대사
Gate 3: 이전·새 버전 호환 시험
Gate 4: 트래픽 전환
Gate 5: 관측 기간 뒤 정리 승인
```

이전 버전 복귀와 새 데이터 읽기까지 리허설하고 실제 복원 시간이 목표 안인지 잰다.

## 4. 자주 실패하는 방식

이미 새 의미로 쓴 데이터를 단순히 컬럼 원복으로 되돌릴 수 있다고 가정하지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

migration checksum, 불일치 비율, 구형 접근과 복구 시험 결과를 연결한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

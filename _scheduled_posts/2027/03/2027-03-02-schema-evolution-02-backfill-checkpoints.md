## 서론: 오늘 해결할 문제

수백만 행을 한 번에 고치면 잠금과 복제 지연이 정상 트래픽을 압박한다.

실행 중인 이전·새 애플리케이션이 같은 DB를 쓰는 상황을 전제로 변경한다. schema와 데이터 이관의 완료 조건을 분리한다.

## 1. 먼저 정할 모델과 계약

backfill은 중단과 중복 실행을 견디는 별도 작업이다. 처리 상한과 완료 범위를 명시한다.

## 2. 설계와 구현의 경계

작은 키 범위로 제한하고 이미 옮긴 행은 건너뛴다. checkpoint는 해당 구간의 commit과 일관되게 저장한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```sql
UPDATE orders
SET normalized_status = status
WHERE id > :lower AND id <= :upper
  AND normalized_status IS NULL;
-- chunk commit 뒤 완료 범위와 남은 행을 대조
```

중간 chunk에서 프로세스를 종료한 뒤 같은 시작점으로 재실행해 중복과 누락을 대사한다.

## 4. 자주 실패하는 방식

OFFSET 진행 위치는 처리 중 데이터 변화에 영향을 받는다. 범위만 지나갔다고 이관 완료로 세지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

처리량, 복제 지연, 남은 미이관 수와 검증 불일치를 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

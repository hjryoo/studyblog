## 서론: 오늘 해결할 문제

컬럼 이름을 한 번에 바꾸면 아직 실행 중인 이전 버전이 즉시 실패한다.

실행 중인 이전·새 애플리케이션이 같은 DB를 쓰는 상황을 전제로 변경한다. schema와 데이터 이관의 완료 조건을 분리한다.

## 1. 먼저 정할 모델과 계약

호환 범위를 넓히는 추가와 오래된 구조를 없애는 제거는 다른 배포다.

## 2. 설계와 구현의 경계

새 구조 추가, 병행 지원, 읽기 전환, 이전 사용 종료 확인, 제거 순서로 나눈다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
V1: old_name만 사용
DB: new_name 추가
V2: 양쪽 호환
이관·검증: new_name 읽기 전환
V1 사용 종료 확인
DB: old_name 제거
```

이전·새 버전을 동시에 실행하며 읽기와 쓰기 호환 행렬을 작성한다.

## 4. 자주 실패하는 방식

새 버전 배포 성공만 보고 기존 컬럼을 삭제하면 rollback과 지연 작업이 깨진다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

구형 필드 접근, 버전별 오류와 제거 전 관측 기간을 기록한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

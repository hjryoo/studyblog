## 서론: 오늘 해결할 문제

기존 불량 데이터가 있는 상태에서 제약을 바로 추가하면 배포가 멈춘다.

실행 중인 이전·새 애플리케이션이 같은 DB를 쓰는 상황을 전제로 변경한다. schema와 데이터 이관의 완료 조건을 분리한다.

## 1. 먼저 정할 모델과 계약

새 입력을 보호하는 규칙과 과거 데이터 전체를 검사하는 비용은 분리할 수 있다.

## 2. 설계와 구현의 경계

지원되는 DB 기능을 확인한 뒤 먼저 신규 위반을 막고 과거 데이터를 정리한다. 예시는 PostgreSQL CHECK 제약이다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```sql
ALTER TABLE orders ADD CONSTRAINT status_present
  CHECK (status IS NOT NULL) NOT VALID;
-- 기존 위반을 별도 정리
ALTER TABLE orders VALIDATE CONSTRAINT status_present;
```

기존 NULL 행과 새 NULL 쓰기를 구분해 제약 적용 시점을 확인한다.

## 4. 자주 실패하는 방식

NOT VALID가 앞으로의 위반도 허용한다고 오해하면 실제 동작을 잘못 설명한다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

기존 위반 수, 신규 거절, validation 시간과 잠금 대기를 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

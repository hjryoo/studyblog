## 서론: 오늘 해결할 문제

캐시 장애 시 전 요청을 DB로 보내면 원본까지 함께 무너질 수 있다.

캐시는 데이터의 복사본이며 원본과 다른 수명과 실패 방식을 갖는다. 적중률뿐 아니라 얼마나 오래 잘못된 값을 허용하는지 설계한다.

## 1. 먼저 정할 모델과 계약

fallback은 무료 우회로가 아니라 추가 부하다. 키 schema 변경도 신구 데이터가 공존하는 배포다.

## 2. 설계와 구현의 경계

원본 동시성 한도와 비필수 기능 축소를 정한다. 새 키 버전은 제한된 warm-up 후 점진 전환한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
v1 읽기 유지
  → v2 제한 warm-up
  → 일부 트래픽 v2
  → 원본 부하·정합성 검증
  → v1 종료와 만료
```

캐시 연결을 끊고 새 namespace를 비운 상태에서 원본 부하와 응답을 비교한다.

## 4. 자주 실패하는 방식

일괄 flush로 문제를 해결하려 하면 대량 miss와 재생성 부하가 발생한다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

fallback QPS, 원본 saturation, 버전별 hit와 거절 비율을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

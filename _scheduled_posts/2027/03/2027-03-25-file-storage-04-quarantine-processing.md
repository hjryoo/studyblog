## 서론: 오늘 해결할 문제

확장자나 Content-Type만 보고 파일을 제공하면 실제 내용과 다를 수 있다.

파일 바이트와 업무 상태를 분리하고 업로드·검증·공개·삭제의 수명주기를 관리한다. 객체 저장소를 사용해도 권한과 정합성 책임은 남는다.

## 1. 먼저 정할 모델과 계약

업로드 성공과 사용 가능한 파일은 다른 상태다. 검증과 변환은 격리된 비동기 작업으로 다룬다.

## 2. 설계와 구현의 경계

PENDING·SCANNING·READY·REJECTED 상태를 두고 검증 전 다운로드를 차단한다. 처리 자원과 시간도 제한한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
PENDING
  → 객체 존재·크기 확인
  → SCANNING: 내용 검증·안전한 변환
  → READY 또는 REJECTED
READY 파일만 다운로드 권한 발급
```

위조된 MIME, 지나치게 큰 이미지와 후처리 실패를 넣어 공개 상태 전이를 확인한다.

## 4. 자주 실패하는 방식

변환 worker에 무제한 메모리와 네트워크 권한을 주면 파일 하나가 장애를 확대한다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

격리 대기 시간, 검증 거절, worker 자원과 상태가 멈춘 파일을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

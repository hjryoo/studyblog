## 서론: 오늘 해결할 문제

큰 offset으로 끝 페이지를 찾거나 색인 갱신 중 넘기면 비용과 결과 변동이 커진다.

검색 결과는 DB 원본, 색인 지연, 분석기와 질의가 결합된 산출물이다. 사용자의 검색 의도와 운영 비용을 함께 검증한다.

## 1. 먼저 정할 모델과 계약

페이지 진행에는 마지막 sort 값과 안정된 정렬, 필요하면 point-in-time이 필요하다.

## 2. 설계와 구현의 경계

지원되는 PIT와 search_after를 사용하고 cursor의 질의·tenant·만료를 함께 묶는다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
첫 요청: 질의·필터·정렬 고정, PIT 생성
응답: 마지막 sort 값으로 cursor 구성
다음 요청: 같은 PIT·질의 + search_after
종료: PIT 해제
만료: 새 검색을 요구
```

동률 점수와 페이지 사이 삽입을 만들어 중복·누락을 검사한다.

## 4. 자주 실패하는 방식

cursor만 전달하고 검색 조건을 바꾸면 이전 정렬 위치의 의미가 달라진다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

페이지별 지연, PIT 수명과 중복·누락, 만료 cursor 거절을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

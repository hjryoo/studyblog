## 서론: 오늘 해결할 문제

테이블 변경 자체는 짧아도 오래된 transaction 뒤에서 기다리며 요청이 밀릴 수 있다.

실행 중인 이전·새 애플리케이션이 같은 DB를 쓰는 상황을 전제로 변경한다. schema와 데이터 이관의 완료 조건을 분리한다.

## 1. 먼저 정할 모델과 계약

DDL의 실행 시간과 잠금 획득 대기는 다르다. 온라인·동시 생성 기능도 무중단을 무조건 보장하지 않는다.

## 2. 설계와 구현의 경계

잠금 timeout, 실행 창과 중단 기준을 정한다. 대상 DB에서 인덱스 생성 실패 후 남는 상태도 확인한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```sql
-- PostgreSQL: transaction 블록 밖에서 실행
CREATE UNIQUE INDEX CONCURRENTLY uq_orders_external
  ON orders (tenant_id, external_id);
-- 적용 전 중복·NULL 정책 확인
-- 실패 후 catalog의 유효 상태 확인
```

장기 transaction이 있는 환경에서 변경을 시도하고 timeout과 재시도를 검증한다.

## 4. 자주 실패하는 방식

PostgreSQL CREATE INDEX CONCURRENTLY를 일반 transaction 블록에 넣으면 실행할 수 없다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

잠금 대기, 인덱스 유효 상태, 쓰기 지연과 디스크 여유를 관측한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

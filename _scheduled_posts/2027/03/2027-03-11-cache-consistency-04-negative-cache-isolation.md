## 서론: 오늘 해결할 문제

없는 상품을 캐시한 뒤 생성했는데 계속 404가 나오거나 권한 차이가 공유될 수 있다.

캐시는 데이터의 복사본이며 원본과 다른 수명과 실패 방식을 갖는다. 적중률뿐 아니라 얼마나 오래 잘못된 값을 허용하는지 설계한다.

## 1. 먼저 정할 모델과 계약

존재하지 않음과 접근할 수 없음은 다른 결과다. 부재 정보에도 TTL과 격리 키가 필요하다.

## 2. 설계와 구현의 경계

negative cache는 짧은 수명과 생성 시 무효화를 둔다. 사용자별 인가 결과를 전역 키에 저장하지 않는다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
NOT_FOUND: 짧은 TTL로 선택적 저장
FORBIDDEN: 사용자·권한 맥락 분리
TIMEOUT: 부재로 저장하지 않음
CREATE 성공: 해당 부재 캐시 무효화
```

생성 직전의 부재 조회와 권한이 다른 두 사용자 접근을 시험한다.

## 4. 자주 실패하는 방식

서버 오류를 없음으로 캐시하면 장애가 복구돼도 잘못된 404가 지속된다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

negative hit, 생성 후 가시화 지연과 오류가 부재로 변환된 사례를 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

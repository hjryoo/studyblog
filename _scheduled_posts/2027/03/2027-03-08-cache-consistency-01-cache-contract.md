## 서론: 오늘 해결할 문제

같은 캐시 정책을 상품 설명과 결제 가능 잔액에 적용하면 업무 위험이 달라진다.

캐시는 데이터의 복사본이며 원본과 다른 수명과 실패 방식을 갖는다. 적중률뿐 아니라 얼마나 오래 잘못된 값을 허용하는지 설계한다.

## 1. 먼저 정할 모델과 계약

정확성 요구와 신선도 예산을 필드별로 정한다. 캐시가 권위 있는 원본인지 단순 가속인지 구분한다.

## 2. 설계와 구현의 경계

키에 tenant와 schema 버전을 포함하고 TTL, 무효화, fallback을 함께 설계한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
key: tenant:t1:product:v2:42
source: product database
staleness budget: 업무가 정한 시간
invalidate: 원본 변경 후
fallback: 제한된 원본 조회
```

원본 갱신 뒤 이전 값이 얼마나 오래 보이는지 측정한다. 재시작과 전체 cache miss도 시험한다.

## 4. 자주 실패하는 방식

적중률만 높이면 오래된 값과 잘못된 사용자별 응답도 좋은 성능으로 계산된다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

hit ratio와 함께 stale 시간, 원본 부하와 잘못된 캐시 공유를 관찰한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

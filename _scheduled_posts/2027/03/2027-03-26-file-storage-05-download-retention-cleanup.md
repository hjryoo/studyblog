## 서론: 오늘 해결할 문제

DB 행 삭제만 끝내면 파일이 남고, 객체부터 지우면 진행 중 요청이 깨질 수 있다.

파일 바이트와 업무 상태를 분리하고 업로드·검증·공개·삭제의 수명주기를 관리한다. 객체 저장소를 사용해도 권한과 정합성 책임은 남는다.

## 1. 먼저 정할 모델과 계약

업무 삭제, 다운로드 권한 만료와 실제 객체 정리는 각각 다른 단계다.

## 2. 설계와 구현의 경계

접근을 먼저 차단하고 삭제 작업을 기록한다. versioning과 복제, 미완료 업로드도 정리 정책에 포함한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
업무 삭제 표시
  → 새 다운로드 발급 차단
  → 삭제 작업 저장
  → 객체·버전 정책에 따른 정리
  → 존재 확인과 완료 기록
```

삭제 요청과 다운로드가 경쟁하는 상황을 재현한다. 실패한 삭제는 재실행 가능한 상태로 남긴다.

## 4. 자주 실패하는 방식

서명 URL은 발급 후 즉시 개별 회수가 어려울 수 있으므로 짧은 만료와 키 정책을 함께 설계한다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

고아 객체, 삭제 지연, 남은 버전과 만료 후 접근을 검증한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

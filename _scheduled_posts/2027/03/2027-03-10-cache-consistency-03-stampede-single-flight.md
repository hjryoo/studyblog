## 서론: 오늘 해결할 문제

인기 키 하나가 만료되면 많은 요청이 동시에 원본을 읽어 장애를 만들 수 있다.

캐시는 데이터의 복사본이며 원본과 다른 수명과 실패 방식을 갖는다. 적중률뿐 아니라 얼마나 오래 잘못된 값을 허용하는지 설계한다.

## 1. 먼저 정할 모델과 계약

동일 키의 재생성 작업을 합치는 single-flight와 요청 동시성 제한은 다른 보호다.

## 2. 설계와 구현의 경계

키별 재생성을 합치고 TTL에 jitter를 둔다. lock을 써도 lease 만료 뒤 중복 작업이 생길 수 있음을 전제한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
cache miss
  → 키별 single-flight 참가
  → 제한된 대표 요청이 재생성
  → 나머지는 짧은 대기 또는 허용된 stale 값
  → timeout이면 명시적 실패
```

인기 키 만료 직후 동시 요청을 보내 실제 DB 조회 횟수를 비교한다.

## 4. 자주 실패하는 방식

재생성 lock 대기 자체에 상한이 없으면 캐시 장애가 요청 스레드 고갈로 바뀐다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

동일 키 동시 재생성 수, 원본 QPS, 대기 시간과 fallback 거절을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

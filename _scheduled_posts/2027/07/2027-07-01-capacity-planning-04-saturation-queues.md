## 서론: 오늘 해결할 문제

부하를 늘려도 완료율은 그대로인데 대기열만 늘면 응답 지연과 timeout이 연쇄적으로 커진다.

평균 응답 시간 하나로 증설을 결정하지 않는다. 수요, 동시 처리, 대기열과 장애 시 여유를 연결해 검증 가능한 용량 계획을 만든다.

## 1. 먼저 정할 모델과 계약

포화점은 처리량뿐 아니라 지연, 오류, 자원 한계와 backlog 변화로 판단한다.

## 2. 설계와 구현의 경계

단계적으로 부하를 올리고 정상 범위, 지연 급증 지점과 회복 시간을 기록한다. 대기열은 유한하게 제한한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
입력 100 → 완료 100, backlog 안정
입력 150 → 완료 145, backlog 증가
입력 200 → 완료 145, 지연·오류 급증
부하 축소 후 backlog 소진 시간 측정
측정값으로 admission·확장 기준 설정
```

입력 부하를 내린 뒤 backlog가 줄어드는지와 timeout 작업이 실제 실행을 멈추는지 확인한다.

## 4. 자주 실패하는 방식

평균 CPU가 낮다고 안전하다고 판단하면 DB lock이나 단일 partition 병목을 놓칠 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

완료율, queue age, pool 대기, lock·I/O와 timeout 후 잔여 작업을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

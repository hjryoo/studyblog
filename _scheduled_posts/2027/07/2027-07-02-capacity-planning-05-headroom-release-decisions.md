## 서론: 오늘 해결할 문제

정상 상태 peak만 간신히 처리하면 노드 한 대 손실이나 rolling 배포 때 목표를 지킬 수 없다.

평균 응답 시간 하나로 증설을 결정하지 않는다. 수요, 동시 처리, 대기열과 장애 시 여유를 연결해 검증 가능한 용량 계획을 만든다.

## 1. 먼저 정할 모델과 계약

용량 계획에는 장애·배포 중 가용 자원과 확장 지연이 들어간다. 여유율은 비용과 위험의 선택이다.

## 2. 설계와 구현의 경계

목표 지연·오류 기준을 정하고 N-1, cold cache와 외부 지연 조건에서 시험한다. 증설 trigger와 중단 기준도 문서화한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
정상 peak → 목표 지연·오류 확인
노드 손실 → 잔여 용량 확인
배포·cold cache → 일시 부하 확인
확장 대기 → 요청 제한·우선순위 확인
출시 결정 → 한계·중단·복구 기준 기록
```

동일 수요에서 일부 인스턴스를 제외한 뒤 서비스 목표와 autoscaling 회복 시간을 확인한다.

## 4. 자주 실패하는 방식

오토스케일이 즉시 준비되거나 DB·외부 API 제한까지 같이 늘어난다고 가정하지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

상태별 안전 도착률, 준비 시간, 비용과 SLO 위반 시간을 비교한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

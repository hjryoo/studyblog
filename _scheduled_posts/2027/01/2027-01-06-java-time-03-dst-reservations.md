## 서론: 오늘 해결할 문제

매일 오전 2시 30분 예약은 DST 전환일에 존재하지 않거나 두 번 나타날 수 있다.

예약·정산 서비스에서는 같은 시각을 저장하고 다시 읽어도 업무상 의미가 보존돼야 한다. 시간 표현, 경계, 테스트를 하나의 계약으로 다룬다.

## 1. 먼저 정할 모델과 계약

지역 시간대에는 gap과 overlap이 있다. 매일 같은 현지 시각과 정확히 24시간 간격은 서로 다른 요구다.

## 2. 설계와 구현의 경계

반복 규칙에 지역과 gap·overlap 처리 정책을 저장한다. 자동 보정에 맡기지 않고 건너뛰기·이동·offset 선택을 명시한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
ZoneId zone = ZoneId.of("Europe/Berlin");
LocalDateTime local = LocalDateTime.of(2027, 3, 28, 2, 30);
var offsets = zone.getRules().getValidOffsets(local);
// 0개: gap, 1개: 정상, 2개: overlap
int choices = offsets.size();
```

Europe/Berlin의 전환일을 골라 유효 offset 개수를 확인한다. 정상일과 전환일의 다음 실행 시각을 비교한다.

## 4. 자주 실패하는 방식

고정 UTC offset을 지역 시간대처럼 쓰면 계절 변경 후 예약이 한 시간 어긋난다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

자동 보정된 예약 수와 중복 실행을 추적한다. 시간대 데이터 업데이트 후 회귀 사례를 재실행한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

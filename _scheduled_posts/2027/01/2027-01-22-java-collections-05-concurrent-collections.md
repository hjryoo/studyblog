## 서론: 오늘 해결할 문제

ConcurrentHashMap을 써도 조회 후 갱신 두 단계를 따로 실행하면 경쟁이 남는다.

컬렉션 선택은 속도뿐 아니라 순서, 중복, 동등성, 변경 권한을 결정한다. 주문 항목과 집계 예제로 숨은 계약을 검증한다.

## 1. 먼저 정할 모델과 계약

스레드 안전한 단일 메서드와 여러 키에 걸친 원자성은 다른 보장이다. 동시성 컬렉션이 전체 업무 트랜잭션을 대신하지 않는다.

## 2. 설계와 구현의 경계

키 하나의 갱신은 merge나 compute로 합친다. 콜백 안의 느린 I/O를 피하고 여러 자원 변경은 별도 일관성 경계를 설계한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
ConcurrentHashMap<String, Long> counts = new ConcurrentHashMap<>();
counts.merge("paid", 1L, Long::sum);
// get + put 대신 키 단위 원자 갱신
long total = counts.getOrDefault("paid", 0L);
```

동일 키를 여러 스레드에서 증가시켜 최종 합계와 경합 시간을 비교한다.

## 4. 자주 실패하는 방식

containsKey 뒤 put을 실행하는 복합 연산은 동시에 삽입될 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

누락 갱신, 키별 경합, 콜백 지연과 메모리 증가를 관찰한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 서론: 오늘 해결할 문제

23시 59분 59초를 하루의 끝으로 잡으면 더 정밀한 timestamp를 누락한다.

예약·정산 서비스에서는 같은 시각을 저장하고 다시 읽어도 업무상 의미가 보존돼야 한다. 시간 표현, 경계, 테스트를 하나의 계약으로 다룬다.

## 1. 먼저 정할 모델과 계약

기간을 시작 포함·끝 제외인 [start, end)로 표현하면 연속 구간을 겹침 없이 연결할 수 있다. Duration과 달력 기반 Period도 구분한다.

## 2. 설계와 구현의 경계

지역 날짜의 시작과 다음 날짜의 시작을 각각 Instant로 변환한다. 저장소 정밀도와 API 정밀도를 맞춰 왕복 시 잘림을 설명한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
LocalDate day = LocalDate.of(2027, 1, 7);
ZoneId zone = ZoneId.of("Asia/Seoul");
Instant from = day.atStartOfDay(zone).toInstant();
Instant until = day.plusDays(1).atStartOfDay(zone).toInstant();
// SQL: occurred_at >= :from AND occurred_at < :until
```

자정 직전 데이터와 다음 날 정확히 자정 데이터를 넣어 단 하루 조회 결과를 확인한다. DST 날의 하루 길이도 고정하지 않는다.

## 4. 자주 실패하는 방식

밀리초 단위를 임의로 더하거나 빼는 방식은 마이크로초 DB와 달력 전환에서 깨진다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

기간 경계 누락과 중복 건수를 검사한다. API·DB 사이 timestamp 정밀도 차이를 기록한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

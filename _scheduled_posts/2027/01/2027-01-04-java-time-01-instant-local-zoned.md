## 서론: 오늘 해결할 문제

생일과 결제 시각을 같은 타입으로 저장하면 시간대 변환 때 의미가 바뀐다.

예약·정산 서비스에서는 같은 시각을 저장하고 다시 읽어도 업무상 의미가 보존돼야 한다. 시간 표현, 경계, 테스트를 하나의 계약으로 다룬다.

## 1. 먼저 정할 모델과 계약

Instant는 시간선 위의 한 지점이고 LocalDate는 달력상의 날짜다. LocalDateTime에는 시간대가 없어 그 자체로 실제 시각을 정하지 못한다.

## 2. 설계와 구현의 경계

사건 발생은 Instant, 영업일은 LocalDate로 모델링한다. 지역의 달력 규칙이 필요한 예약에는 ZoneId와 현지 시각을 함께 보존한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
Instant paidAt = Instant.parse("2027-01-04T00:00:00Z");
ZoneId seoul = ZoneId.of("Asia/Seoul");
ZonedDateTime display = paidAt.atZone(seoul);
LocalDate birthday = LocalDate.of(1995, 4, 12);
```

동일 Instant를 서울과 뉴욕에 표시하고 생일에는 변환을 적용하지 않는다. API의 필드별 의미를 문서와 테스트에 적는다.

## 4. 자주 실패하는 방식

서버 기본 시간대에 의존하면 컨테이너나 개발 환경이 바뀔 때 저장 값이 달라진다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

환경별 직렬화 결과와 DB 왕복 결과가 동일한지 검사한다. offset이 없는 사건 시각 입력은 거절한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현

```

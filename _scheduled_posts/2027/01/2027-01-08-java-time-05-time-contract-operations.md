## 서론: 오늘 해결할 문제

API는 UTC인데 배치 기준일은 서버 현지 날짜라면 같은 거래가 다른 날 정산될 수 있다.

예약·정산 서비스에서는 같은 시각을 저장하고 다시 읽어도 업무상 의미가 보존돼야 한다. 시간 표현, 경계, 테스트를 하나의 계약으로 다룬다.

## 1. 먼저 정할 모델과 계약

사건 시각, 수집 시각, 업무 기준일은 서로 다른 데이터다. 하나를 다른 값에서 암묵적으로 추론하면 재처리 결과가 달라진다.

## 2. 설계와 구현의 경계

경계마다 timezone과 기준일 계산 규칙을 명시한다. 지연 도착 데이터는 당시 업무 날짜와 재처리 실행 시각을 따로 남긴다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
occurredAt: 2027-01-07T15:30:00Z
businessZone: Asia/Seoul
businessDate: 2027-01-08
processedAt: 2027-01-09T02:00:00Z
재처리해도 businessDate는 동일
```

같은 원본을 하루 뒤 재처리해도 정산 귀속일이 같아야 한다. 운영 화면에는 표시 timezone을 함께 보여 준다.

## 4. 자주 실패하는 방식

모든 날짜를 UTC 날짜로 자르는 것은 지역 영업일을 보존하는 정책이 아니다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

지연 도착 비율, 귀속일 변경 건수, 스케줄러 실행일과 대상일 차이를 대조한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

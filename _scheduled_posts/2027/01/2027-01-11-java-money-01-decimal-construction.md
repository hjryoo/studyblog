## 서론: 오늘 해결할 문제

double에서 넘어온 0.1을 정확한 십진 금액이라고 가정하면 오차가 그대로 보존된다.

주문 금액은 계산 가능성뿐 아니라 통화, 반올림 시점, 재현 가능한 정산 규칙을 가져야 한다. 단위와 정책을 코드 경계에 드러낸다.

## 1. 먼저 정할 모델과 계약

BigDecimal은 정밀한 십진 연산을 제공하지만 입력이 이미 근사값이면 의도를 복원하지 못한다. 숫자 표현과 업무 금액을 구분한다.

## 2. 설계와 구현의 경계

외부 금액은 십진 문자열로 받고 통화별 허용 scale을 검증한다. 계산 중간 값과 최종 청구 금액의 정밀도 정책을 나눈다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
BigDecimal exact = new BigDecimal("0.10");
BigDecimal total = exact.multiply(new BigDecimal("3"));
BigDecimal charge = total.setScale(2, RoundingMode.UNNECESSARY);
// charge = 0.30
```

문자열 생성과 double 생성 결과를 비교하고 합산·직렬화·DB 왕복까지 검증한다.

## 4. 자주 실패하는 방식

생성 후 setScale만 호출하면 잘못된 입력 원인을 숨기고 조용히 금액을 바꿀 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

허용 scale 초과 입력과 예상치 못한 반올림을 집계한다. 합계 불변 조건을 테스트한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현

```

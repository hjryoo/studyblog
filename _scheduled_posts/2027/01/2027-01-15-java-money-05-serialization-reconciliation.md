## 서론: 오늘 해결할 문제

서버가 정확히 계산해도 JSON 소비자가 double로 읽거나 DB가 scale을 자르면 결과가 달라진다.

주문 금액은 계산 가능성뿐 아니라 통화, 반올림 시점, 재현 가능한 정산 규칙을 가져야 한다. 단위와 정책을 코드 경계에 드러낸다.

## 1. 먼저 정할 모델과 계약

BigDecimal의 equals는 scale도 비교하지만 compareTo는 수치 크기를 비교한다. 동등성·정렬·해시 키 정책을 일관되게 정한다.

## 2. 설계와 구현의 경계

API에는 통화와 십진 문자열 또는 최소 단위 정수를 계약으로 제공한다. DB precision과 scale, 반올림 책임을 명시한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
BigDecimal x = new BigDecimal("1.0");
BigDecimal y = new BigDecimal("1.00");
boolean numericEqual = x.compareTo(y) == 0; // true
boolean objectEqual = x.equals(y);        // false
// API 예: {"amount":"1.00","currency":"USD"}
```

서버→JSON→소비자→DB 왕복 후 원금·통화·배분 합계를 대사한다.

## 4. 자주 실패하는 방식

compareTo로는 같고 equals로는 다른 값을 중복 키로 혼용하면 집계가 갈라진다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

수치 동등성, scale 보존 여부, 일별 대사 불일치 건수와 금액을 추적한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 서론: 오늘 해결할 문제

항목별 반올림의 합과 전체 합산 후 반올림은 결과가 다를 수 있다.

주문 금액은 계산 가능성뿐 아니라 통화, 반올림 시점, 재현 가능한 정산 규칙을 가져야 한다. 단위와 정책을 코드 경계에 드러낸다.

## 1. 먼저 정할 모델과 계약

반올림은 자료형의 기술 옵션이면서 금액 정책의 일부다. 단가, 세액, 할인, 청구 단계별 적용 순서를 정해야 한다.

## 2. 설계와 구현의 경계

업무 규칙이 정한 지점에서만 scale을 줄인다. 나눗셈에는 scale 또는 MathContext를 명시하고 오차를 허용하는 단계를 기록한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
BigDecimal a = new BigDecimal("0.005");
BigDecimal b = new BigDecimal("0.005");
BigDecimal perItem = a.setScale(2, RoundingMode.HALF_UP)
    .add(b.setScale(2, RoundingMode.HALF_UP));
BigDecimal atEnd = a.add(b).setScale(2, RoundingMode.HALF_UP);
// perItem=0.02, atEnd=0.01
```

0.005처럼 경계에 걸리는 값과 음수 환불을 같은 테스트 집합에 넣는다.

## 4. 자주 실패하는 방식

계산식 곳곳에 HALF_UP을 복사하면 정책 변경 때 일부 경로만 바뀐다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

정산 오차의 절댓값과 방향, 항목 합계와 청구액 차이를 대조한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현

  → 관측 결과 비교
  → 운영 절차에 반영
```

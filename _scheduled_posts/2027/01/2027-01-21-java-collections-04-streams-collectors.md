## 서론: 오늘 해결할 문제

toMap의 중복 키 예외를 임의 병합으로 없애면 중요한 오류까지 숨긴다.

컬렉션 선택은 속도뿐 아니라 순서, 중복, 동등성, 변경 권한을 결정한다. 주문 항목과 집계 예제로 숨은 계약을 검증한다.

## 1. 먼저 정할 모델과 계약

Stream은 원본을 변형하지 않는 데이터 변환 파이프라인으로 다루는 편이 이해하기 쉽다. 키 충돌 정책은 업무 규칙이다.

## 2. 설계와 구현의 경계

중복이면 실패할지 합칠지 명시하고 순서가 필요하면 Map 공급자도 지정한다. 외부 가변 상태를 람다에서 수정하지 않는다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
record Line(String sku, int qty) {}
Map<String, Integer> quantities = lines.stream().collect(
    Collectors.toMap(Line::sku, Line::qty,
        Math::addExact, LinkedHashMap::new));
// lines의 유효성 검사는 수집 전에 수행
```

같은 SKU의 수량을 합산하되 오버플로와 음수 수량을 별도로 검증한다.

## 4. 자주 실패하는 방식

병렬 Stream이 외부 ArrayList를 수정하면 데이터 경쟁과 순서 불확실성이 생긴다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

입력·출력 합계 보존, 중복 키 처리, 빈 입력과 순서 계약을 검사한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 서론: 오늘 해결할 문제

상태 코드와 nullable 필드 조합이 늘어나면 존재하면 안 되는 응답도 만들 수 있다.

잘못된 상태와 변환을 컴파일 단계에서 줄이면 검증 코드와 운영 예외가 줄어든다. 공개 API와 도메인 경계에 타입 정보를 남긴다.

## 1. 먼저 정할 모델과 계약

record는 값 데이터를 표현하고 sealed 계층은 허용된 하위 타입을 제한한다. 원소까지 자동으로 불변이 되는 것은 아니다.

## 2. 설계와 구현의 경계

성공·대기·거절처럼 서로 다른 결과를 별도 타입으로 만든다. 각 타입 생성 시 필요한 값과 검증을 모은다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
sealed interface Result permits Accepted, Rejected {}
record Accepted(String orderId) implements Result {}
record Rejected(String reason) implements Result {}
// 각 결과는 자신에게 필요한 값만 보유
```

거절 응답에 성공 ID가 섞이는 잘못된 상태를 타입으로 제거한다.

## 4. 자주 실패하는 방식

record에 가변 List를 그대로 담으면 외부 수정으로 값의 동등성이 바뀔 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

불가능한 상태의 표현 경로, 누락된 결과 분기와 방어적 복사를 검사한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

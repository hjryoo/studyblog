## 서론: 오늘 해결할 문제

회고에서 나온 개선안이 담당자 없는 할 일 목록으로만 남으면 같은 문제가 다음 분기에 반복된다.

연말에 검토한 가정과 부채를 새해의 작은 검증 실험으로 연결한다. 결정의 소유자와 종료 조건이 있어야 회고가 실행으로 이어진다.

## 1. 먼저 정할 모델과 계약

기술 도입과 문제 해결을 구분하고 가장 위험한 가정을 검증 가능한 질문으로 바꾼다. 완료 기준에는 사용자 결과와 운영 비용을 함께 둔다.

## 2. 설계와 구현의 경계

각 실험에 소유자, 기간, 비교 대상, 성공·중단 기준을 기록한다. 큰 이관 전에 작은 트래픽 또는 데이터 범위로 위험을 낮춘다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```yaml
experiment: search-read-model
owner: search-team
hypothesis: reduce tail latency
comparison: same dataset and traffic
exit: latency target and cost budget both met
rollback: retain current read path
```

검색 지연 개선을 예로 같은 데이터와 부하에서 기존 구현과 후보를 비교한다. 실패하면 폐기할 수 있는 산출물로 시작한다.

## 4. 자주 실패하는 방식

도구 설치나 PoC 완성을 업무 성과로 세면 실제 사용자 문제는 그대로 남을 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

실험 종료율, 결정까지의 기간, 반증된 가정과 되돌림 비용을 기록한다. 결과는 원래 ADR에 연결한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

## 시리즈 마무리

이번 연재의 설계 기준을 실제 서비스 한 곳에 적용하고 변경 전후 결과를 기록하자. 개선 여부는 예제의 성공뿐 아니라 실패 상황에서도 계약이 유지되는지로 판단한다.

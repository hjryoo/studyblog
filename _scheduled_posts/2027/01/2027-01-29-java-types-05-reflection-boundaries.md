## 서론: 오늘 해결할 문제

리플렉션 기반 공통 처리기가 모든 객체를 허용하면 잘못된 설정이 운영에서 드러난다.

잘못된 상태와 변환을 컴파일 단계에서 줄이면 검증 코드와 운영 예외가 줄어든다. 공개 API와 도메인 경계에 타입 정보를 남긴다.

## 1. 먼저 정할 모델과 계약

런타임 탐색은 컴파일 단계의 보장을 줄인다. 접근 가능성과 타입 호환성, 모듈 경계는 별도로 검증해야 한다.

## 2. 설계와 구현의 경계

플러그인 등록 시 생성자와 인터페이스를 검사하고 시작 단계에 실패시킨다. 일반 업무 경로는 명시적 인터페이스를 호출한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
Class<?> candidate = Class.forName(className);
Class<? extends Runnable> taskType = candidate.asSubclass(Runnable.class);
Runnable task = taskType.getDeclaredConstructor().newInstance();
// 예제는 공개 무인자 생성자를 갖는 등록 타입을 가정
```

잘못된 구현 타입과 없는 생성자를 주입해 기동 검증이 잡는지 확인한다.

## 4. 자주 실패하는 방식

예외를 삼키고 null을 반환하면 원인과 실패 위치가 사라진다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

기동 검증 실패와 런타임 탐색 비용을 분리해 기록한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

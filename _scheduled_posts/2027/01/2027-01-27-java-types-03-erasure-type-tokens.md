## 서론: 오늘 해결할 문제

List<Order>와 List<Customer>는 런타임에서 같은 raw class로 보일 수 있다.

잘못된 상태와 변환을 컴파일 단계에서 줄이면 검증 코드와 운영 예외가 줄어든다. 공개 API와 도메인 경계에 타입 정보를 남긴다.

## 1. 먼저 정할 모델과 계약

타입 소거로 일반 타입 매개변수의 정보 일부가 실행 시점에 사라진다. Class<T>는 원소 타입을 자동 검증하는 만능 도구가 아니다.

## 2. 설계와 구현의 경계

직렬화 경계에는 프레임워크가 제공하는 매개변수화 타입 표현을 사용한다. unchecked cast는 검증한 단일 adapter로 좁힌다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
JSON 배열
  → List.class: 원소의 Order 정보 없음
  → 매개변수화된 List<Order> 타입 정보 제공
  → 원소별 schema 검증
  → 도메인 변환
```

빈 목록과 잘못된 원소 타입이 섞인 목록을 역직렬화해 검증 위치를 확인한다.

## 4. 자주 실패하는 방식

raw List로 역직렬화한 뒤 전체를 List<Order>로 캐스팅하면 오류 발견이 늦어진다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

역직렬화 실패, unchecked cast 위치와 raw type 사용을 점검한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현

```

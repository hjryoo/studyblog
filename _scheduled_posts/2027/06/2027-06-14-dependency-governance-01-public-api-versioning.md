## 서론: 오늘 해결할 문제

메서드 이름을 유지해도 예외 종류나 기본 동작을 바꾸면 사용자가 깨질 수 있다.

라이브러리 변경은 배포한 서비스들의 계약 변경이다. 버전 번호, 실제 호환성, 전이 의존성과 업데이트 절차를 따로 확인한다.

## 1. 먼저 정할 모델과 계약

SemVer는 공개 API와 그 호환성 정책이 먼저 있어야 의미가 있다. 소스·바이너리·동작 호환성은 구분한다.

## 2. 설계와 구현의 경계

지원 패키지와 확장 지점, 오류 계약과 직렬화 형식을 문서화한다. 구현 세부사항은 공개 범위에서 제외한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
public interface PricePolicy {
    Money quote(OrderDraft order);
}
// quote의 예외·반올림·null 계약도 공개 약속이다.
// 내부 구현 클래스는 소비자가 직접 참조하지 않게 한다.
```

기존 사용자 코드를 새 라이브러리로 컴파일하고 기존 바이너리를 새 버전과 실행하는 시험을 분리한다.

## 4. 자주 실패하는 방식

버전 숫자만 보고 모든 런타임 조합과 데이터 형식까지 호환된다고 단정하지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

공개 API 변화, 소비자 빌드 실패와 동작 변경 사례를 기록한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

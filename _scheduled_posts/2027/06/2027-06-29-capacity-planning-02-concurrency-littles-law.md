## 서론: 오늘 해결할 문제

초당 요청 수가 같아도 외부 API 지연이 늘면 동시에 대기하는 작업 수가 증가한다.

평균 응답 시간 하나로 증설을 결정하지 않는다. 수요, 동시 처리, 대기열과 장애 시 여유를 연결해 검증 가능한 용량 계획을 만든다.

## 1. 먼저 정할 모델과 계약

안정된 시스템에서 평균 동시 작업 수 L은 평균 도착률 λ와 평균 체류 시간 W의 곱이다. 같은 경계와 단위를 사용한다.

## 2. 설계와 구현의 경계

전체 요청과 DB 연결 점유 구간을 구분해 계산하고 pool 크기를 단순히 전체 동시성으로 결정하지 않는다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
λ = 200 requests/second
W = 0.15 second
L = λ × W = 30 requests
DB 연결 점유 0.02 second라면 해당 경계 평균은 4
필요 pool 크기는 분산·여유·DB 한계까지 검증
```

초당 200건에 평균 0.15초라면 평균 동시 요청은 30건이다. 지연이 두 배일 때 관측과 비교한다.

## 4. 자주 실패하는 방식

p99 지연을 평균 W에 그대로 넣거나 포화로 대기열이 계속 증가하는 상황에 안정 상태 공식을 적용하지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

도착·완료율, 평균 체류 시간과 실제 in-flight를 같은 시간창에서 비교한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

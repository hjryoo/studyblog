## 서론: 오늘 해결할 문제

캐시를 켰는데 전체 시간이 줄지 않는다면 다운로드·테스트·업로드가 더 큰 비중일 수 있다.

빠른 빌드의 전제는 같은 입력에 같은 결과가 나오는 것이다. 작업 그래프, 입력 선언, 의존성과 캐시를 분리해 점검한다.

## 1. 먼저 정할 모델과 계약

빌드 시간은 설정, 임계 경로의 실행, 대기와 외부 전송으로 나눠 측정한다.

## 2. 설계와 구현의 경계

cold·warm build와 변경 유형별 표본을 분리하고 가장 큰 병목 한 개를 먼저 개선한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```bash
./gradlew help --profile
./gradlew test --profile
./gradlew assemble --profile
# 로컬 profile 보고서를 같은 조건의 기준선과 비교한다.
# cold/warm 여부와 runner 사양을 함께 기록한다.
```

같은 runner 자원과 JDK에서 반복 측정해 중앙값과 느린 구간을 비교한다.

## 4. 자주 실패하는 방식

병렬도만 늘리면 메모리 압박과 외부 서비스 경합으로 오히려 느려질 수 있다. 외부 build scan 공유 시 정보 노출도 검토한다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

전체 소요와 실패율, critical path, runner 메모리와 queue 시간을 함께 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

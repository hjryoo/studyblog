## 서론: 오늘 해결할 문제

가상 사용자 수를 고정한 시험에서는 응답이 느려질수록 다음 요청도 늦어져 과부하를 덜 드러낼 수 있다.

평균 응답 시간 하나로 증설을 결정하지 않는다. 수요, 동시 처리, 대기열과 장애 시 여유를 연결해 검증 가능한 용량 계획을 만든다.

## 1. 먼저 정할 모델과 계약

폐쇄 모델은 동시 사용자 흐름을, 개방 모델은 도착률을 중심으로 부하를 만든다. 실제 수요 특성에 맞춰 선택한다.

## 2. 설계와 구현의 경계

k6의 arrival-rate executor로 도착률을 고정하고 VU 부족으로 시작하지 못한 반복도 함께 측정한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```javascript
import http from "k6/http";
export const options = { scenarios: { arrivals: {
  executor: "constant-arrival-rate", rate: 50, timeUnit: "1s",
  duration: "1m", preAllocatedVUs: 20, maxVUs: 100
}}};
export default function () {
  http.get(`${__ENV.BASE_URL}/test/orders`);
}
```

아래 k6 예시는 테스트 허가를 받은 격리 환경의 BASE_URL에서만 실행한다. 목표 도착률과 완료율을 따로 확인한다.

## 4. 자주 실패하는 방식

부하 발생기가 먼저 포화되거나 dropped iterations를 무시하면 서버 용량을 잘못 해석한다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

시도·시작·완료율, dropped iterations, 부하 발생기 CPU와 서버 지연을 함께 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

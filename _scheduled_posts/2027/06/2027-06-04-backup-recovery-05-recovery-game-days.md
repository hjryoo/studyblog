## 서론: 오늘 해결할 문제

복원 담당자가 없거나 서비스 전환 권한이 누락되면 좋은 백업도 복구 목표를 지키지 못한다.

백업 파일 생성과 서비스 복구는 다른 결과다. PostgreSQL을 예로 데이터, 인증 정보, 외부 저장소와 재처리 절차를 함께 점검한다.

## 1. 먼저 정할 모델과 계약

훈련은 복원 도구뿐 아니라 판단, 승인, 트래픽 전환과 재발 방지까지 검증한다.

## 2. 설계와 구현의 경계

복구 지점 선택과 쓰기 차단, 대사, 전환, 원래 구성으로 복귀할 조건을 runbook에 적는다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
사고 선언 → 쓰기·영향 범위 판단
백업·WAL 검증 → 격리 복원
업무 대사 → 전환 승인
트래픽 전환 → 새 쓰기 확인
복귀 필요 시 변경분 대사부터 계획
```

백업 하나의 손상과 담당자 부재를 가정하고 대체 경로로 목표를 지킬 수 있는지 확인한다.

## 4. 자주 실패하는 방식

훈련 중 새로 생긴 데이터를 생각하지 않고 원래 DB로 돌아가면 또 다른 데이터 손실이 생긴다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

단계별 소요, 수동 판단, 복귀 시 대사 결과와 다음 개선 담당자를 남긴다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

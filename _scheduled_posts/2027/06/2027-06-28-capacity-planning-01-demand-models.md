## 서론: 오늘 해결할 문제

가입자 수만으로 서버를 계산하면 활성 비율과 화면별 요청 증폭을 놓친다.

평균 응답 시간 하나로 증설을 결정하지 않는다. 수요, 동시 처리, 대기열과 장애 시 여유를 연결해 검증 가능한 용량 계획을 만든다.

## 1. 먼저 정할 모델과 계약

수요는 도착률, 업무 혼합과 payload 분포로 정의한다. peak·burst와 배치 경합도 별도로 본다.

## 2. 설계와 구현의 경계

업무별 빈도와 호출 fan-out을 측정해 DB·외부 API에 전달되는 부하를 추정한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
예시: 활성 사용자 3,000명
평균 30초마다 업무 요청 1회 → 약 100 req/s
조회 80 req/s, 생성 20 req/s
생성당 외부 호출 2회 → 추가 40 calls/s
실측 peak와 분포로 가정을 교정
```

주문 조회 80%, 생성 20%인 학습용 혼합을 기준으로 요청·쿼리·외부 호출 수를 비교한다.

## 4. 자주 실패하는 방식

전체 요청을 가벼운 health check로 대체하면 서비스가 실제로 처리할 수 있는 양을 과장한다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

업무별 도착률, payload 크기, fan-out과 peak 지속 시간을 기록한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

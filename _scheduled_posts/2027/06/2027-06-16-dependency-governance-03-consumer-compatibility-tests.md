## 서론: 오늘 해결할 문제

라이브러리 자체 테스트가 통과해도 서비스가 쓰는 방식과 프레임워크 조합은 다를 수 있다.

라이브러리 변경은 배포한 서비스들의 계약 변경이다. 버전 번호, 실제 호환성, 전이 의존성과 업데이트 절차를 따로 확인한다.

## 1. 먼저 정할 모델과 계약

호환성은 지원 대상 조합에서 검증해야 한다. API diff와 소비자 실행 시험은 서로 보완한다.

## 2. 설계와 구현의 경계

대표 소비자 fixture와 지원 JDK·프레임워크 matrix를 작게 유지하고 직렬화·설정·오류 동작을 포함한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
축 A: 지원 JDK
축 B: 라이브러리 구·신 버전
사례: API 호출, 설정, 예외, 직렬화
검증: 기존 바이너리 실행 + 소비자 재컴파일
모든 조합 대신 실제 지원 조합을 명시
```

이전 버전에서 만든 입력을 새 버전에서 읽고 rolling 배포 중 구·신 버전 교환도 확인한다.

## 4. 자주 실패하는 방식

성공 호출만 시험하면 에러 타입, 기본값과 설정 이름 변화가 빠진다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

matrix별 실패, 데이터 왕복 결과와 미지원 조합을 구분해 공개한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

## 서론: 오늘 해결할 문제

잠긴 버전도 취약할 수 있고 신뢰하지 않은 artifact를 받으면 고정만으로 안전해지지 않는다.

라이브러리 변경은 배포한 서비스들의 계약 변경이다. 버전 번호, 실제 호환성, 전이 의존성과 업데이트 절차를 따로 확인한다.

## 1. 먼저 정할 모델과 계약

버전 선택, 다운로드한 내용 검증, 취약점 평가와 런타임 권한은 서로 다른 방어다.

## 2. 설계와 구현의 경계

공식 저장소와 checksum·서명 검증 정책을 정한다. 자동 생성된 검증 메타데이터도 신뢰 기준과 대조한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
업데이트 후보
  → 변경·보안 공지 확인
  → graph·lockfile diff
  → artifact 검증 메타데이터 리뷰
  → 소비자 시험·canary
  → 예외·롤백 조건 기록
```

업데이트 PR에서 lockfile, 전이 의존성, 검증 메타데이터와 소비자 시험 결과를 함께 리뷰한다.

## 4. 자주 실패하는 방식

검증 파일을 다운로드한 값으로 무조건 갱신하면 변조된 내용도 새 정상값으로 승인할 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

검증 실패, 미분류 취약점과 예외 만료일을 본다. Gradle 공식 dependency verification 문서도 함께 확인한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

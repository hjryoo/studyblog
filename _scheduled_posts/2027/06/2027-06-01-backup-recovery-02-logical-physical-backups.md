## 서론: 오늘 해결할 문제

테이블 일부를 옮기는 요구와 대용량 인스턴스를 빠르게 복원하는 요구는 다르다.

백업 파일 생성과 서비스 복구는 다른 결과다. PostgreSQL을 예로 데이터, 인증 정보, 외부 저장소와 재처리 절차를 함께 점검한다.

## 1. 먼저 정할 모델과 계약

논리 백업은 객체와 데이터를 재생성하고 물리 백업은 데이터 파일 기반으로 복원한다. 호환성과 복원 범위를 구분한다.

## 2. 설계와 구현의 경계

크기·허용 복원 시간·버전 조건에 맞게 방식을 선택한다. 역할과 전역 객체, 확장, 설정도 별도로 확인한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```bash
pg_dump -Fc -d training_source -f training.dump
createdb recovery_drill
pg_restore --exit-on-error -d recovery_drill training.dump
# 대상 DB와 권한은 실행 전에 별도로 확인한다.
```

아래 명령은 접근 권한이 제한된 훈련 환경에서만 실행한다. 별도 recovery_drill DB를 사용하고 원본에는 복원하지 않는다.

## 4. 자주 실패하는 방식

운영 중 데이터 디렉터리를 단순 복사하면 일관된 물리 백업이 된다고 가정해서는 안 된다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

백업 시간뿐 아니라 복원 소요, 누락된 역할·확장과 무결성 검증 결과를 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

## 서론: 오늘 해결할 문제

캐시 적중률이 높아도 입력 누락으로 잘못된 산출물을 재사용하면 빌드 품질은 나빠진다.

빠른 빌드의 전제는 같은 입력에 같은 결과가 나오는 것이다. 작업 그래프, 입력 선언, 의존성과 캐시를 분리해 점검한다.

## 1. 먼저 정할 모델과 계약

UP-TO-DATE는 로컬 출력 재사용, build cache는 출력 복원, configuration cache는 설정 단계 재사용이다.

## 2. 설계와 구현의 경계

캐시마다 재사용 대상을 구분하고 비캐시 빌드를 기준선으로 산출물을 비교한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
기준: 비캐시 빌드 결과
비교 A: 입력 변경 없이 로컬 재실행
비교 B: 새 checkout에서 build cache 복원
비교 C: 입력 변경 후 재실행
각 산출물과 실행 이유를 대조
```

입력 경로와 환경을 바꾼 뒤 캐시 사용·미사용 결과를 비교하고 remote cache 쓰기 권한을 제한한다.

## 4. 자주 실패하는 방식

configuration cache를 켰다고 Task 출력까지 자동으로 원격 공유되는 것은 아니다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

각 캐시 적중 사유, 잘못된 재사용, 캐시 전송 비용과 신뢰 경계를 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

## 서론: 오늘 해결할 문제

Deprecated 표시만 하고 대체 경로나 기한이 없으면 소비자는 변경을 미루게 된다.

라이브러리 변경은 배포한 서비스들의 계약 변경이다. 버전 번호, 실제 호환성, 전이 의존성과 업데이트 절차를 따로 확인한다.

## 1. 먼저 정할 모델과 계약

폐기 정책은 대체 API, 차이, 지원 기간과 제거 조건의 계약이다. 이미 배포한 버전의 내용은 바꾸지 않는다.

## 2. 설계와 구현의 경계

마이그레이션 예제와 릴리스 노트를 제공하고 실제 사용 소비자를 확인한다. 문제 수정은 새 버전으로 낸다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```java
@Deprecated(since = "2.4", forRemoval = false)
Money calculate(OrderDraft draft) {
    return quote(draft).total();
}
// 이 위임이 기존 예외·반올림 계약도 유지하는지 검증한다.
```

대표 소비자를 대체 API로 옮기며 문서만으로 변경을 끝낼 수 있는지 검증한다.

## 4. 자주 실패하는 방식

문자열 타입이 같아도 의미가 달라진 API는 단순 이름 교체로 마이그레이션할 수 없다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

구 API 사용 수, 지원 버전 분포와 마이그레이션 실패를 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

이번 연재의 설계 기준을 실제 서비스 한 곳에 적용하고 변경 전후 결과를 기록하자. 개선 여부는 예제의 성공뿐 아니라 실패 상황에서도 계약이 유지되는지로 판단한다.

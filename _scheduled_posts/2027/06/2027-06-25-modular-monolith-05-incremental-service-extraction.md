## 서론: 오늘 해결할 문제

깔끔한 모듈이라고 바로 별도 서비스로 떼면 네트워크 실패와 데이터 일관성 비용을 놓친다.

배포 단위가 하나여도 업무 경계는 필요하다. Spring Modulith를 참고해 패키지 구조, 공개 계약, 이벤트와 테스트로 경계를 검증한다.

## 1. 먼저 정할 모델과 계약

모듈 경계는 분리 후보이지 자동 분리 보장이 아니다. 호출 지연·부분 실패·배포 독립성의 비용이 추가된다.

## 2. 설계와 구현의 경계

분리 이유와 데이터 소유권을 확인하고 계약·timeout·재시도·중복 처리부터 준비한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
업무 모듈 + 명시적 계약
  → 경계 테스트·데이터 소유권 정리
  → 원격 adapter와 실패 계약
  → 제한된 트래픽으로 전환
  → 데이터 쓰기 권한 분리
분리 이득이 비용보다 큰지 재평가
```

동일 계약을 로컬 구현과 원격 adapter로 실행해 결과와 실패 차이를 비교한다.

## 4. 자주 실패하는 방식

데이터베이스를 계속 양쪽이 직접 수정하면 배포만 분리되고 데이터 결합은 남는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

교차 호출 수, 분산 트랜잭션 필요성, 운영 비용과 독립 배포 이득을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

## 서론: 오늘 해결할 문제

요청 중 플래그 값이 바뀌면 입력 검증과 저장 정책이 서로 달라질 수 있다.

배포와 기능 공개를 분리하되 플래그도 수명과 장애 방식을 가진 운영 자원으로 다룬다. 분기마다 소유자와 제거 조건을 남긴다.

## 1. 먼저 정할 모델과 계약

설정 전파에는 지연이 있고 한 업무에서 필요한 판단 안정성은 별도로 보장해야 한다.

## 2. 설계와 구현의 경계

요청 시작 시 평가 결과를 고정하고 장기 작업에는 사용한 정책 버전을 저장한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
요청 시작: policyVersion=17 평가
검증·계산·저장: 동일 평가 결과 사용
다음 요청: 최신 version 평가
장기 작업: 시작 정책 또는 재평가 지점을 명시
```

실행 중 플래그를 바꿔 이미 시작한 업무가 어떤 정책으로 끝나는지 확인한다.

## 4. 자주 실패하는 방식

로컬 cache가 즉시 전역 변경을 반영할 것이라 가정하지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

설정 version 분포, 전파 지연과 한 업무 내 평가 불일치를 관측한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

## 서론: 오늘 해결할 문제

짧은 요청 폭증을 모두 거절하거나 전부 허용하면 사용자 경험과 용량이 함께 흔들린다.

받을 수 없는 요청을 일찍 제한해야 정상 요청의 지연을 보호할 수 있다. 처리량, 동시 실행과 공정성을 별도 제어한다.

## 1. 먼저 정할 모델과 계약

보충률은 장기 허용량, bucket 크기는 단기 burst 예산이다.

## 2. 설계와 구현의 경계

시간 단위를 명시하고 토큰 갱신·소비를 같은 원자 연산으로 처리한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
tokens = min(capacity, tokens + elapsedSeconds * refillPerSecond)
요청 비용 cost <= tokens: 소비 후 허용
그 외: 거절 또는 제한된 대기
갱신·판단·소비는 원자적으로 수행
```

긴 유휴 뒤 burst와 지속 과부하를 보내 허용량이 정책과 맞는지 확인한다.

## 4. 자주 실패하는 방식

여러 인스턴스가 각자 전체 한도를 가지면 총 허용량이 인스턴스 수만큼 늘 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

토큰 잔량, 허용·거절 수와 인스턴스별 편차를 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.

- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

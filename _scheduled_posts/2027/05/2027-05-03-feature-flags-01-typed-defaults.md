## 서론: 오늘 해결할 문제

플래그 제공자가 응답하지 않을 때 어떤 기능이 켜지는지 정하지 않으면 장애 중 동작이 바뀐다.

배포와 기능 공개를 분리하되 플래그도 수명과 장애 방식을 가진 운영 자원으로 다룬다. 분기마다 소유자와 제거 조건을 남긴다.

## 1. 먼저 정할 모델과 계약

타입이 있는 평가와 기본값은 정상적인 실패 처리 계약이다. 기본값의 안전성은 기능별로 다르다.

## 2. 설계와 구현의 경계

각 플래그에 기본값과 fallback 이유를 적고 설정 검증을 시작 단계에 수행한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
flag: new-checkout
type: boolean
default: false
provider 장애: 기존 checkout 경로
평가 결과와 fallback 이유를 함께 기록
```

제공자 없음·잘못된 타입·지연을 주입해 기본값과 오류 기록을 확인한다.

## 4. 자주 실패하는 방식

권한 검사를 단순 기능 플래그로 대체하면 공개 범위와 접근 권한이 혼동된다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

평가 오류, fallback 비율과 기본값 상태의 사용자 영향을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

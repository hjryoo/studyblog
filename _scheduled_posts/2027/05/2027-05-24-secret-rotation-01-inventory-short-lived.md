## 서론: 오늘 해결할 문제

어떤 서비스가 오래된 키를 쓰는지 모르면 폐기 순간 장애가 난다.

비밀은 값 자체보다 발급·전달·교체·폐기 과정에서 관리해야 한다. 정상 교체와 유출 대응이 같은 관측 가능한 경로를 사용하게 만든다.

## 1. 먼저 정할 모델과 계약

비밀마다 소유자·소비자·권한·만료와 교체 방법이 있어야 한다.

## 2. 설계와 구현의 경계

장기 고정 값보다 가능한 짧은 수명 자격 증명을 사용하고 발급 실패를 설계한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
secret: orders-db
owner: orders-team
consumers: api, batch
permissions: 필요한 schema·동작
expiry: 명시
rotation: 발급 → 검증 → 전환 → 폐기
```

서비스 하나의 비밀을 골라 마지막 사용 위치와 실제 권한을 확인한다.

## 4. 자주 실패하는 방식

이름만 dev·prod로 나누고 실제 권한을 공유하면 격리가 되지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

만료 잔여일, 마지막 사용, 장기 비밀 수와 소유자 누락을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

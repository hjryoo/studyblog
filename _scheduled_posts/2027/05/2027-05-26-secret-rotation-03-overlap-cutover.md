## 서론: 오늘 해결할 문제

새 키 배포가 끝나기 전에 옛 키를 폐기하면 일부 인스턴스만 인증에 실패한다.

비밀은 값 자체보다 발급·전달·교체·폐기 과정에서 관리해야 한다. 정상 교체와 유출 대응이 같은 관측 가능한 경로를 사용하게 만든다.

## 1. 먼저 정할 모델과 계약

두 버전을 잠시 허용하는 기간과 최종 폐기 조건을 함께 정의한다.

## 2. 설계와 구현의 경계

신규 발급→일부 전환→전체 적용 확인→옛 키 사용 종료→폐기 순으로 진행한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
V2 발급, V1 유지
V2 canary 검증
전체 소비자 V2 전환
V1 사용 종료 확인
V1 폐기, 실패·잔여 사용 감시
```

늦게 갱신되는 batch와 장기 연결을 포함해 회전을 리허설한다.

## 4. 자주 실패하는 방식

중첩 기간을 무기한 늘리면 오래된 키가 사실상 계속 유효하다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

옛 키 마지막 사용, 적용률, 인증 오류와 중첩 기간 초과를 추적한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

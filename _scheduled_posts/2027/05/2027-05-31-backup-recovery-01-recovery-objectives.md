## 서론: 오늘 해결할 문제

매일 백업이 성공해도 허용 가능한 데이터 손실이 10분이면 목표에 맞지 않는다.

백업 파일 생성과 서비스 복구는 다른 결과다. PostgreSQL을 예로 데이터, 인증 정보, 외부 저장소와 재처리 절차를 함께 점검한다.

## 1. 먼저 정할 모델과 계약

RPO는 허용할 데이터 손실 구간이고 RTO는 서비스 복구에 허용할 시간이다. 둘 다 업무 단위의 합의가 필요하다.

## 2. 설계와 구현의 경계

복구 대상과 의존 시스템을 목록화하고 탐지·판단·복원·검증 시간을 나눠 예산을 정한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
예시 목표: RPO 10분, RTO 60분
탐지·판단: 10분
복원: 30분
데이터 검증·서비스 전환: 20분
의존성: DB, 객체, 키, 설정, 외부 대사
```

주문 DB와 객체 저장소를 함께 복원한다고 가정해 어느 시점의 조합이 유효한지 확인한다.

## 4. 자주 실패하는 방식

DB가 실행되는 시점을 복구 완료로 잡으면 결제 대사와 사용자 접근 복구 시간이 빠진다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

실제 복원 지점, 검증 완료 시각과 미복구 의존성을 기록한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

## 서론: 오늘 해결할 문제

필요 없는 사용자 정보를 편의상 저장하면 백업과 분석으로도 복제된다.

데이터를 수집한 순간부터 저장·로그·분석·삭제 경로까지 추적한다. 특정 법률 해석이 아니라 불필요한 노출을 줄이는 소프트웨어 설계에 집중한다.

## 1. 먼저 정할 모델과 계약

필드의 목적, 소유자와 이동 경로가 있어야 최소 수집을 판단할 수 있다.

## 2. 설계와 구현의 경계

요청 필드에서 DB·로그·이벤트·외부 전송으로 이어지는 데이터 흐름을 적는다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
필드: 연락처
목적: 배송 알림
원본: 고객 입력
복사: 주문 DB, 알림 서비스
제외: 일반 로그·분석 이벤트
보존·삭제 책임자 지정
```

기능 한 개를 골라 실제 trace와 schema가 문서의 필드 목록과 맞는지 확인한다.

## 4. 자주 실패하는 방식

DB 컬럼만 조사하면 예외 로그와 임시 export에 남은 정보를 놓친다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

소유자 없는 필드, 미사용 수집 항목과 문서 밖 전달을 찾는다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

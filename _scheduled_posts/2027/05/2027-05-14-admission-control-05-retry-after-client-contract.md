## 서론: 오늘 해결할 문제

429를 받은 모든 client가 동시에 재시도하면 다음 구간도 같은 폭증이 반복된다.

받을 수 없는 요청을 일찍 제한해야 정상 요청의 지연을 보호할 수 있다. 처리량, 동시 실행과 공정성을 별도 제어한다.

## 1. 먼저 정할 모델과 계약

거절은 API 계약이며 retry 가능성과 대기 안내를 명확히 해야 한다.

## 2. 설계와 구현의 경계

정책에 맞는 Retry-After와 제한된 backoff·jitter를 제공하고 전체 deadline을 유지한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```http
HTTP/1.1 429 Too Many Requests
Retry-After: 5
Content-Type: application/json

{"code":"RATE_LIMITED","retryable":true}
```

다수 client의 재시도 시점을 분산해 입력 부하가 회복되는지 측정한다.

## 4. 자주 실패하는 방식

지수 backoff만 있고 시도 상한이 없으면 오래된 업무가 계속 자원을 소비한다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

거절 후 재시도 증폭, 성공까지 시간과 기한 초과를 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

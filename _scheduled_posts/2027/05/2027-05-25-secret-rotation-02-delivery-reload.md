## 서론: 오늘 해결할 문제

비밀 저장소 값을 바꿨는데 애플리케이션은 시작할 때 읽은 값을 계속 사용할 수 있다.

비밀은 값 자체보다 발급·전달·교체·폐기 과정에서 관리해야 한다. 정상 교체와 유출 대응이 같은 관측 가능한 경로를 사용하게 만든다.

## 1. 먼저 정할 모델과 계약

저장소 갱신과 소비자의 적용은 별도 사건이다. 연결 pool에는 이전 인증 연결이 남을 수 있다.

## 2. 설계와 구현의 경계

동적 reload 또는 재시작 방식을 명시하고 새 연결 검증·pool 교체를 설계한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
새 secret version 발급
  → 소비자 감지 또는 재배포
  → 신규 연결 검증
  → 기존 pool drain
  → 적용 version 보고
```

비밀 값을 교체한 뒤 새 연결과 기존 연결이 각각 어떤 버전을 사용하는지 확인한다.

## 4. 자주 실패하는 방식

환경 변수 변경만으로 이미 실행 중인 프로세스 값이 자동 교체된다고 가정하지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

소비자별 version, 새 연결 인증 실패와 reload 시간을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

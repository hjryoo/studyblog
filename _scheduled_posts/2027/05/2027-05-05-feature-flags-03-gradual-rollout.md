## 서론: 오늘 해결할 문제

10% 공개라고 해도 고비용 고객이 몰리면 실제 부하와 위험은 10%가 아니다.

배포와 기능 공개를 분리하되 플래그도 수명과 장애 방식을 가진 운영 자원으로 다룬다. 분기마다 소유자와 제거 조건을 남긴다.

## 1. 먼저 정할 모델과 계약

공개 비율, 고객 선택과 관측 기준을 함께 정의해야 rollout을 평가할 수 있다.

## 2. 설계와 구현의 경계

내부·대표 고객·일부 비율 순으로 확대하고 각 단계의 유지 시간과 중단 조건을 둔다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
내부 사용자
  → 대표 고객
  → 안정된 5% cohort
  → SLI·용량 검증
  → 확대 또는 즉시 기존 경로 복귀
```

같은 cohort에서 오류와 지연, 업무 성공을 기존 경로와 비교한다.

## 4. 자주 실패하는 방식

원인 분석 전에 여러 플래그를 동시에 바꾸면 어느 변경이 영향을 줬는지 알기 어렵다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

cohort별 오류·지연·성공과 처리량, 되돌림 반영 시간을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

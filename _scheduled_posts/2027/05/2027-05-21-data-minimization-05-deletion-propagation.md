## 서론: 오늘 해결할 문제

주 DB에서 지웠어도 cache·검색·분석 모델과 복원된 백업에서 다시 나타날 수 있다.

데이터를 수집한 순간부터 저장·로그·분석·삭제 경로까지 추적한다. 특정 법률 해석이 아니라 불필요한 노출을 줄이는 소프트웨어 설계에 집중한다.

## 1. 먼저 정할 모델과 계약

삭제 완료는 관련 복사본의 상태를 포함하는 workflow로 정의해야 한다.

## 2. 설계와 구현의 경계

삭제 요청 ID와 대상 범위를 저장하고 각 시스템 확인을 모은다. 복원 후 재적용할 삭제 기록도 관리한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
삭제 요청 등록
  → 원본 접근 차단
  → DB·cache·검색·export 정리
  → 대상별 완료 확인
복원 시: 보존된 삭제 지시 재적용
```

부분 실패와 백업 복원 뒤 재삭제를 격리 환경에서 시험한다.

## 4. 자주 실패하는 방식

즉시 삭제와 지연 정리의 차이를 숨기면 완료 상태를 잘못 보고한다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

시스템별 삭제 지연, 미확인 대상과 복원 후 재출현을 검증한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

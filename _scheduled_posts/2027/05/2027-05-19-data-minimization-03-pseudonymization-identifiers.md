## 서론: 오늘 해결할 문제

이메일을 단순 해시로 바꿔도 작은 후보 집합을 대입하면 원문을 추측할 수 있다.

데이터를 수집한 순간부터 저장·로그·분석·삭제 경로까지 추적한다. 특정 법률 해석이 아니라 불필요한 노출을 줄이는 소프트웨어 설계에 집중한다.

## 1. 먼저 정할 모델과 계약

연결 가능한 식별자는 여전히 재식별 위험이 있다. 목적별 ID와 원문 접근 권한을 분리한다.

## 2. 설계와 구현의 경계

필요한 경우 별도 비밀로 보호한 HMAC과 목적별 namespace를 사용한다. 키 회전과 연결 기간도 정한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
원문 사용자 ID
  → purpose-specific HMAC 또는 별도 무작위 ID
  → 분석에는 가명 ID만 전달
연결 표·키는 별도 최소 권한
가명화와 익명화의 보장을 구분
```

동일 목적의 연결성과 다른 목적 사이의 분리를 확인한다.

## 4. 자주 실패하는 방식

가명 ID를 공개해도 무해하다고 단정하거나 원문과 같은 저장소에 모든 연결 표를 두지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

원문 접근, 목적 간 식별자 재사용과 key version 사용을 감사한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

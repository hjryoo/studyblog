## 서론: 오늘 해결할 문제

보안 문서에 회전 주기가 있어도 실제 교체가 시험되지 않으면 장애 시 처음 실행하게 된다.

비밀은 값 자체보다 발급·전달·교체·폐기 과정에서 관리해야 한다. 정상 교체와 유출 대응이 같은 관측 가능한 경로를 사용하게 만든다.

## 1. 먼저 정할 모델과 계약

회전 성공은 값 변경이 아니라 전체 소비자 전환과 이전 권한 폐기까지다.

## 2. 설계와 구현의 경계

정기 훈련과 실패 주입으로 절차를 검증하고 운영자가 필요한 권한도 확인한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
훈련 계획
  → 비밀 값 없는 실행 기록
  → 일부 소비자 실패 주입
  → 복구·폐기까지 확인
  → 소유자·Runbook 갱신
```

발급 서비스 장애와 일부 소비자 전환 실패를 넣어 중단·되돌림 기준을 시험한다.

## 4. 자주 실패하는 방식

회전 작업 로그에 실제 secret 값을 남기면 감사가 새 유출 경로가 된다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

회전 완료율, 만료 위반, 수동 개입과 폐기 확인을 기록한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

## 시리즈 마무리

이번 연재의 설계 기준을 실제 서비스 한 곳에 적용하고 변경 전후 결과를 기록하자. 개선 여부는 예제의 성공뿐 아니라 실패 상황에서도 계약이 유지되는지로 판단한다.

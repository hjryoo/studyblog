## 서론: 오늘 해결할 문제

같은 사용자가 요청마다 서로 다른 실험군에 들어가면 결과와 경험이 흔들린다.

배포와 기능 공개를 분리하되 플래그도 수명과 장애 방식을 가진 운영 자원으로 다룬다. 분기마다 소유자와 제거 조건을 남긴다.

## 1. 먼저 정할 모델과 계약

targeting key와 context는 대상 선택의 입력이다. 서버의 신뢰한 사용자·tenant 맥락에서 구성한다.

## 2. 설계와 구현의 경계

원문 이메일 대신 안정된 내부 식별자를 검토하고 요청별 context를 격리한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```json
{"targetingKey":"tenant-t1:user-u7",
 "tenantId":"t1",
 "plan":"standard",
 "region":"kr"}

```

같은 사용자의 반복 요청과 다른 tenant의 동일 로컬 ID를 평가해 일관성을 확인한다.

## 4. 자주 실패하는 방식

공유된 전역 context를 요청마다 바꾸면 다른 사용자의 평가에 섞일 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

대상 선택 변경, context 누락과 개인정보 속성 전송을 검사한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

## 서론: 오늘 해결할 문제

실험이 끝난 뒤 분기와 설정이 남으면 테스트 조합과 운영 실수가 계속 늘어난다.

배포와 기능 공개를 분리하되 플래그도 수명과 장애 방식을 가진 운영 자원으로 다룬다. 분기마다 소유자와 제거 조건을 남긴다.

## 1. 먼저 정할 모델과 계약

플래그에는 도입 목적, 소유자, 검토일과 제거 조건이 필요하다.

## 2. 설계와 구현의 경계

최종 경로 확정 후 구형 실행이 없는지 관측하고 코드·설정·테스트를 순서대로 정리한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
결론 승인
  → 구형 경로 사용 종료 확인
  → 코드 분기 제거·배포
  → 이전 버전 종료 확인
  → 설정 삭제와 감사 기록
```

오래된 client와 배포 버전이 남은 상태에서 설정 삭제 영향을 시험한다.

## 4. 자주 실패하는 방식

설정부터 삭제하면 기본값으로 떨어진 구형 코드가 예상과 반대로 동작할 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

기한 지난 플래그, 분기 수, 구형 평가 요청과 제거 후 fallback을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

이번 연재의 설계 기준을 실제 서비스 한 곳에 적용하고 변경 전후 결과를 기록하자. 개선 여부는 예제의 성공뿐 아니라 실패 상황에서도 계약이 유지되는지로 판단한다.

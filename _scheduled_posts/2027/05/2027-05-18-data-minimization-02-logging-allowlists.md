## 서론: 오늘 해결할 문제

요청 전체를 로그로 남긴 뒤 마스킹하면 새 필드가 추가될 때 노출이 생길 수 있다.

데이터를 수집한 순간부터 저장·로그·분석·삭제 경로까지 추적한다. 특정 법률 해석이 아니라 불필요한 노출을 줄이는 소프트웨어 설계에 집중한다.

## 1. 먼저 정할 모델과 계약

허용된 운영 필드만 기록하는 방식은 금지 필드 목록보다 기본 노출 범위를 줄인다.

## 2. 설계와 구현의 경계

event name·상태·상관 ID를 구조화하고 본문·토큰·쿠키는 기본 제외한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```json
{"event":"order.validation_failed",
 "requestId":"r42","field":"postalCode",
 "reason":"INVALID_FORMAT"}

```

새 민감 필드를 요청에 추가해도 기존 로깅 코드가 자동 출력하지 않는지 시험한다.

## 4. 자주 실패하는 방식

예외 메시지나 HTTP header에 민감 값이 섞이면 정상 로그 정책을 우회할 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

민감 패턴 탐지, 로그 크기와 허용 목록 밖 필드 출현을 확인한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

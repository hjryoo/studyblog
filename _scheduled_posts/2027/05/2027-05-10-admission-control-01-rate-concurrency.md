## 서론: 오늘 해결할 문제

요청 수는 그대로인데 외부 API가 느려지면 처리 중인 요청이 쌓여 자원이 고갈된다.

받을 수 없는 요청을 일찍 제한해야 정상 요청의 지연을 보호할 수 있다. 처리량, 동시 실행과 공정성을 별도 제어한다.

## 1. 먼저 정할 모델과 계약

초당 도착률과 동시에 처리 중인 작업 수는 다른 값이다. 지연 증가가 동시성을 높인다.

## 2. 설계와 구현의 경계

rate limit과 concurrency limit을 분리하고 대기열에도 상한을 둔다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
입력 100 req/s
평균 처리 0.1s → 약 10 in-flight
평균 처리 2s → 약 200 in-flight
rate limit + 동시성 한도 + 대기 상한을 별도 설계
```

일정한 입력률에서 외부 지연만 늘려 in-flight와 메모리 변화를 측정한다.

## 4. 자주 실패하는 방식

QPS 제한 하나만으로 느린 의존성이 만드는 자원 고갈을 막을 수 없다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

도착·완료율, in-flight, 큐 대기와 거절을 함께 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

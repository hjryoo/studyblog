## 서론: 오늘 해결할 문제

lease가 만료돼 새 worker가 시작됐는데 이전 worker가 늦게 돌아와 결과를 덮을 수 있다.

여러 서비스에 걸친 업무를 재시작 가능한 상태 전이로 모델링한다. 프로세스 메모리와 실제 업무 진행 상태를 분리한다.

## 1. 먼저 정할 모델과 계약

lease는 실행 자격의 수명이고 fencing token은 오래된 실행의 결과를 거절하는 순서 표식이다.

## 2. 설계와 구현의 경계

작업 획득 때 세대 번호를 증가시키고 상태 저장과 외부 자원도 지원 가능한 검증을 적용한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```sql
UPDATE workflows
SET state = :next_state
WHERE id = :id AND generation = :claimed_generation
  AND state = :expected_state;
-- 영향 행 수 0이면 오래된 실행 또는 상태 충돌
```

worker A를 멈춰 lease가 만료된 뒤 B가 처리하게 하고 A의 늦은 결과를 거절한다.

## 4. 자주 실패하는 방식

분산 lock 획득만으로 모든 외부 부작용의 단일 실행을 보장하지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

lease 만료, stale token 거절, 중복 실행과 heartbeat 지연을 관측한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교

```

## 서론: 오늘 해결할 문제

운영자가 DB 상태만 강제로 바꾸면 외부 시스템과 이력이 어긋날 수 있다.

여러 서비스에 걸친 업무를 재시작 가능한 상태 전이로 모델링한다. 프로세스 메모리와 실제 업무 진행 상태를 분리한다.

## 1. 먼저 정할 모델과 계약

수동 복구도 허용된 상태 전이와 감사 기록을 갖는 운영 API로 다루는 편이 안전하다.

## 2. 설계와 구현의 경계

중단·재개·보상 명령에 현재 상태 검사와 권한을 적용한다. 변경 이유와 예상 효과를 기록한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
운영자: 현재 상태·외부 결과 확인
  → 예상 전이 검토
  → 권한 있는 재개 명령
  → 제한된 실행
  → 결과 대사·감사 기록
```

오래 멈춘 업무 하나를 선택해 모의 복구하고 외부 상태까지 대사한다.

## 4. 자주 실패하는 방식

전체 backlog 재실행은 외부 API 한도와 데이터 부작용을 함께 증폭시킬 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

미결 업무 나이, 수동 개입 수, 복구 성공과 동일 원인 반복을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.

- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

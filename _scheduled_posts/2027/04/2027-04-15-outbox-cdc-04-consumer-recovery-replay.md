## 서론: 오늘 해결할 문제

새 읽기 모델을 재생하면서 이메일이나 외부 결제까지 다시 실행하면 사고가 난다.

DB 변경과 외부 사건 발행 사이의 빈틈을 줄이고, 전달 지연과 재처리를 운영한다. 로컬 원자성과 전체 전달 보장을 구분한다.

## 1. 먼저 정할 모델과 계약

상태 projection과 외부 부작용은 다른 소비 경로다. replay 목적과 대상 범위를 명시한다.

## 2. 설계와 구현의 경계

dedup 저장과 projection 변경을 원자적으로 처리하고 외부 호출은 별도 멱등 키를 사용한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
replay 대상: 주문 검색 projection
외부 부작용 handler: 실행 제외
event ID·aggregate version: 중복·역순 검사
완료: 원본과 표본 대사
전환: catch-up 위치 확인
```

같은 사건 집합을 두 번 재생해 읽기 결과와 외부 호출 수가 안정적인지 확인한다.

## 4. 자주 실패하는 방식

offset을 되돌리는 행위를 단순 조회 재실행처럼 취급하지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

replay 속도, projection lag, 중복 방어와 외부 부작용 건수를 비교한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

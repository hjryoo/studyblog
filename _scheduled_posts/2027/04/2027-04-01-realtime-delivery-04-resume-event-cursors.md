## 서론: 오늘 해결할 문제

모바일 네트워크가 바뀐 뒤 연결만 다시 열면 끊긴 동안의 이벤트는 사라질 수 있다.

알림과 진행 상태 전송은 연결 유지보다 재접속·권한·과부하 처리가 어렵다. 연결과 업무 이벤트의 수명을 분리한다.

## 1. 먼저 정할 모델과 계약

연결은 일시적이고 재생 cursor는 논리적 진행 위치다. cursor의 범위와 보존 기간을 명시한다.

## 2. 설계와 구현의 경계

이벤트 ID와 제한된 재생 저장소를 두고 오래된 cursor에는 전체 상태 재동기화를 제공한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
client: 마지막 확인 ID=42
재접속: Last-Event-ID 42
server: 인가 후 43 이후 재생
보존 범위 밖: 전체 상태 조회 요구
client: ID 기준 중복 제거
```

전송 직후 연결을 끊고 같은 이벤트가 다시 와도 client가 멱등 처리하는지 확인한다.

## 4. 자주 실패하는 방식

메모리에만 이벤트를 두면 인스턴스 교체 후 재생을 보장할 수 없다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

재생 성공률, cursor 만료, 중복 이벤트와 상태 재동기화 시간을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.
- [ ] 모델의 책임과 외부 의존성의 경계를 구분했다.
- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

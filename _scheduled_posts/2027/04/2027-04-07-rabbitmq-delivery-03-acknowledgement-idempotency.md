## 서론: 오늘 해결할 문제

ack 후 DB가 실패하면 메시지는 사라지고 업무 결과가 남지 않는다.

주문 후속 처리에서 전송·저장·소비 완료를 각각 다른 보장으로 다룬다. 재전송과 중복을 전제로 처리 경계와 운영 신호를 설계한다.

## 1. 먼저 정할 모델과 계약

수동 ack는 처리 완료를 알리는 경계다. DB commit과 broker ack는 하나의 원자 연산이 아니다.

## 2. 설계와 구현의 경계

업무 변경과 dedup 기록을 같은 transaction에 저장한 뒤 ack한다. ack 유실 시 재전달을 안전하게 무시한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
메시지 E42 수신
  → transaction: dedup E42 + 업무 변경
  → DB commit
  → broker ack
재전달 E42: 기존 처리 확인 후 ack
```

DB commit 직후 worker를 종료해 재전달 시 변경이 두 번 적용되지 않는지 검사한다.

## 4. 자주 실패하는 방식

메모리 Set에만 처리 ID를 두면 재시작 뒤 중복을 막지 못한다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

재전달률, dedup hit, 미확인 메시지와 DB commit 실패를 연결한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 서론: 오늘 해결할 문제

처리할 수 없는 메시지를 즉시 requeue하면 같은 실패가 CPU와 로그를 소모한다.

주문 후속 처리에서 전송·저장·소비 완료를 각각 다른 보장으로 다룬다. 재전송과 중복을 전제로 처리 경계와 운영 신호를 설계한다.

## 1. 먼저 정할 모델과 계약

일시적 장애와 영구 입력 오류는 다른 retry 정책이 필요하다.

## 2. 설계와 구현의 경계

시도 횟수와 간격을 제한하고 초과 메시지는 원인·원본 event ID와 함께 격리한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
일시 실패 → 지연 retry
시도 상한 초과 → dead-letter
영구 schema 오류 → 즉시 격리
원인 수정 → 검토된 재처리
재처리도 원래 event ID 유지
```

잘못된 payload와 일시 DB 장애를 넣어 각각 격리·회복되는지 확인한다.

## 4. 자주 실패하는 방식

dead letter에 넣는 것만으로 해결되지 않는다. 소유자와 재처리 완료 기준이 필요하다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

retry 증폭, 가장 오래된 격리 메시지와 원인별 실패를 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

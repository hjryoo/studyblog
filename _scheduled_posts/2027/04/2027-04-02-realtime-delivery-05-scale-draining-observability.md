## 서론: 오늘 해결할 문제

서버를 증설해도 기존 장기 연결은 자동으로 새 서버에 균등 분배되지 않는다.

알림과 진행 상태 전송은 연결 유지보다 재접속·권한·과부하 처리가 어렵다. 연결과 업무 이벤트의 수명을 분리한다.

## 1. 먼저 정할 모델과 계약

접속 분산, 이벤트 전달 경로와 인스턴스 종료는 서로 다른 운영 문제다.

## 2. 설계와 구현의 경계

instance별 연결 상한과 drain 시간을 정한다. pub/sub만 쓸 경우 재생 보장을 별도로 둔다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
종료 시작
  → 새 연결 거절·readiness 전환
  → 진행 중 전송 마무리
  → client에 재접속 유도
  → deadline 후 종료, cursor로 복구
```

rolling 배포 중 연결 재수립과 이벤트 누락, 재접속 폭증을 측정한다.

## 4. 자주 실패하는 방식

sticky session만으로 이벤트 영속성과 장애 복구까지 해결되지는 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

instance별 연결 수, drain 시간, 재접속 peak와 메시지 전달 지연을 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

## 서론: 오늘 해결할 문제

tenant_id가 요청에 있다는 이유만으로 그 고객의 데이터를 읽을 권한이 생기지는 않는다.

하나의 서비스에서 여러 고객의 데이터와 자원을 다룰 때 격리는 모든 경계를 통과해야 한다. 인증된 tenant 맥락을 저장소와 비동기 작업까지 전달한다.

## 1. 먼저 정할 모델과 계약

tenant 선택과 해당 tenant에 대한 권한 검사는 별개의 단계다.

## 2. 설계와 구현의 경계

인증 정보와 멤버십으로 tenant를 확정하고 내부 context로 전달한다. async 실행 시 복사와 정리를 명시한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
사용자 인증
  → tenant 선택 요청
  → 멤버십·권한 검증
  → 신뢰한 TenantContext 생성
  → DB·cache·작업에 전달, 종료 시 정리
```

권한 없는 tenant ID와 thread pool 재사용으로 다른 요청의 맥락이 남는 사례를 시험한다.

## 4. 자주 실패하는 방식

ThreadLocal을 정리하지 않으면 다음 요청이 이전 tenant 맥락을 사용할 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

tenant 결정 실패, 누락 context와 교차 고객 접근 거절을 확인한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

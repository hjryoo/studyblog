## 서론: 오늘 해결할 문제

외부 호출 timeout이 났어도 상대 시스템은 이미 작업을 끝냈을 수 있다.

여러 서비스에 걸친 업무를 재시작 가능한 상태 전이로 모델링한다. 프로세스 메모리와 실제 업무 진행 상태를 분리한다.

## 1. 먼저 정할 모델과 계약

전송 실패, 명시적 거절과 결과 불명은 서로 다른 상태다.

## 2. 설계와 구현의 경계

업무 키로 상대 상태를 조회하거나 같은 멱등 키로 재호출한다. 확인 없이 반대 작업을 먼저 시작하지 않는다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
외부 요청 key=wf42-step2
응답 timeout → UNKNOWN
상대 상태 조회 또는 동일 key 재요청
확인된 결과만 상태 전이에 사용
확인 불가 → 기한 있는 수동 대응
```

응답 직전 네트워크를 끊고 조회·재시도가 같은 최종 결과를 만드는지 시험한다.

## 4. 자주 실패하는 방식

결과 불명 상태를 즉시 실패로 바꾸면 성공한 결제를 다시 요청할 수 있다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

불명 상태 비율, 해소 시간과 멱등 키별 중복 효과를 본다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

## 실전 체크리스트

- [ ] 오늘의 문제에 대한 기대 결과를 테스트로 표현했다.

- [ ] 예제의 정상·경계·실패 입력을 각각 실행했다.
- [ ] 실패 후 재실행과 복구 결과를 확인했다.
- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

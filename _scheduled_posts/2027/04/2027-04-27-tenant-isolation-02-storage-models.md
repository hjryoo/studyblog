## 서론: 오늘 해결할 문제

고객마다 DB를 나누면 격리는 쉬워지지만 연결과 migration 운영 비용이 늘어난다.

하나의 서비스에서 여러 고객의 데이터와 자원을 다룰 때 격리는 모든 경계를 통과해야 한다. 인증된 tenant 맥락을 저장소와 비동기 작업까지 전달한다.

## 1. 먼저 정할 모델과 계약

pool·silo·혼합 모델은 보안, 복원, 규모와 운영 부담의 다른 trade-off다.

## 2. 설계와 구현의 경계

고객별 복구 요구와 부하 편차, 데이터 크기를 먼저 평가한다. 선택 기준과 예외 고객 이관 경로를 문서화한다.

## 3. 작은 예제로 확인하기

아래 예제는 핵심 동작을 설명하기 위한 발췌다. 실제 적용 시에는 프로젝트의 타입, 권한, 의존성 버전에 맞춰 완성해야 한다.

```text
공유 테이블: tenant 키와 모든 접근 경계 검증
분리 schema: 이름 선택·migration 운영
분리 DB: credential·connection·backup 운영
혼합: 일관된 tenant routing 계약 필요
```

고객 하나를 독립적으로 백업·복구하는 시간을 모델별로 비교한다.

## 4. 자주 실패하는 방식

DB가 분리돼도 cache나 로그, 운영 API가 공유되면 tenant 격리가 완성되지 않는다.

정상 경로를 확인한 다음 이 실패 조건을 별도 사례로 재현한다. 실패 시 데이터가 어떻게 남는지와 재실행 결과까지 확인해야 복구 절차를 정할 수 있다.

## 5. 관측과 검증

고객당 연결·비용, 복원 시간과 migration 대상 수를 추적한다.

측정 범위와 비교 조건을 고정한다. 같은 입력과 부하에서 변경 전후를 비교하고, 통과 기준을 배포 전에 기록한다.

## 적용 순서

```text
업무 입력과 기대 결과 정의
  → 모델·경계 구현
  → 예제와 실패 조건 재현
  → 관측 결과 비교
  → 운영 절차에 반영
```

- [ ] 핵심 지표와 변경 전후 비교 결과를 남겼다.

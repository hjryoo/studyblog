## 서론: 오늘의 문제

단위 테스트 비율이라는 숫자만으로 품질을 설명할 수 없다. 변경이 깨뜨릴 수 있는 계약과 실패 비용을 기준으로 테스트 수준과 실행 빈도를 배치한다.

## 1. 위험 목록 만들기

금액 계산, 권한, 데이터 손실, 외부 계약처럼 실패 비용이 큰 동작을 먼저 적는다. 코드 줄 수보다 사용자 영향과 변경 빈도를 테스트 투자 기준으로 삼는다.

## 2. 단위 테스트의 역할

순수한 도메인 규칙과 경계 조건을 빠르게 검증한다. mock 호출 순서를 구현과 똑같이 복제하기보다 입력과 관찰 가능한 결과를 확인한다.

## 3. 통합 테스트의 역할

DB schema, transaction, serialization, framework 설정처럼 실제 조합에서만 드러나는 계약을 검증한다. 모든 경우를 느린 테스트로 옮기지 않고 대표 경로를 선택한다.

## 4. End-to-end의 제한

소수의 핵심 사용자 흐름으로 배포 가능성을 확인하되 데이터와 외부 환경 불안정성을 통제한다. 세부 오류 위치는 더 낮은 수준의 테스트가 설명하게 한다.

## 5. 실행 계층

PR에는 빠른 필수 검사, merge 후에는 넓은 통합, 주기 작업에는 장시간 회귀와 복원 시험을 배치한다. 실패 결과의 담당자와 수정 SLA도 정한다.

## 6. 자주 실패하는 방식

커버리지 목표를 채우기 위해 의미 없는 assert를 늘리면 변경 자신감이 높아지지 않는다. 모든 의존성을 mock하면 실제 SQL과 네트워크 계약이 배포 후 처음 실행된다.

## 7. 관측과 검증

위험 영역별 테스트 존재, 결함 발견 단계, 테스트 실행 시간, 변경 실패율, flaky 비율, 회귀가 production까지 도달한 시간을 본다. 기준값은 정상 시간대와 변경 전후를 비교해 정하고, 점검 결과가 실제 행동으로 이어지는지 정기적으로 확인한다.

## 실행 흐름

```text
1. 위험 목록 만들기
   ↓
2. 단위 테스트의 역할
   ↓
3. 통합 테스트의 역할
   ↓
```

개별 도구보다 이 순서를 팀의 설계 리뷰와 Runbook에 남기는 것이 중요하다. 상황이 달라져도 판단 근거와 검증 결과가 이어져야 한다.

- [ ] 통합 테스트의 역할: 기준과 책임자를 문서화했다.
- [ ] End-to-end의 제한: 기준과 책임자를 문서화했다.
- [ ] 실행 계층: 기준과 책임자를 문서화했다.
